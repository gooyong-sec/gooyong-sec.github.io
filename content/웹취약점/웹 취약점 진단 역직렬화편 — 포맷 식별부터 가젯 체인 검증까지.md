## 1. Java — `ObjectInputStream`, 가젯 체인, URLDNS

### 원리·단서 기능·성립 조건

Java 네이티브 직렬화는 객체의 필드뿐 아니라 타입 정보를 담습니다. `ObjectInputStream.readObject()`는 그래프를 복원하면서 클래스의 `readObject()`, `readResolve()`, 비교기, 컬렉션 콜백 등을 호출할 수 있습니다. ysoserial은 서버 클래스패스에 이미 있는 이런 호출을 연결한 **가젯 체인 생성기**이지, 어느 Java 서버에서나 통하는 범용 익스플로잇이 아닙니다.

쿠키·숨은 필드·요청 본문을 Base64 디코딩했을 때 처음 네 바이트가 `ac ed 00 05`인지 봅니다.

```bash
printf '%s' 'rO0AB...' | base64 -d | xxd -l 8
# 기대 단서: aced 0005
```

URLDNS 체인은 `java.net.URL`의 해시 계산 과정에서 이름 해석을 유발해 **클래스패스 의존성이 거의 없는 탐지용 체인**으로 쓰입니다. 그러나 콜백이 왔다는 것은 역직렬화 경로와 DNS 도달성을 보여줄 뿐, 명령 실행 가젯의 존재를 증명하지 않습니다. 실제 진단에서는 조직이 관리하는 격리 DNS 수신기를 써야 하며, 이 글은 인터넷 콜백 주소나 데이터 유출 절차를 제공하지 않습니다.

### 따라하기 — PortSwigger `Exploiting Java deserialization with Apache Commons`

- 랩: [Exploiting Java deserialization with Apache Commons](https://portswigger.net/web-security/deserialization/exploiting/lab-deserialization-exploiting-java-deserialization-with-apache-commons)
- 제공 계정으로 로그인해 `session` 쿠키를 URL 디코딩·Base64 디코딩하고 Java 헤더를 확인합니다.
- 공식 랩 지침대로 랩에 존재하는 `CommonsCollections4` 체인을 생성해 **Academy 인스턴스가 지정한 파일만** 대상으로 풉니다.
- Base64 결과를 쿠키에 넣고 다시 URL 인코딩해 요청합니다.

성공 기준은 랩 배너의 완료 표시입니다. 로컬·운영 시스템에 ysoserial 페이로드를 시험하지 않습니다. URLDNS를 안전한 사전 탐지로 사용할 때의 성공 기준은 요청별 nonce를 포함한 단 한 번의 DNS 질의이며, HTTP 콜백이나 RCE로 과장하지 않습니다.

### 진단 체크리스트와 오탐 구분

- Base64 디코딩 후 실제 `AC ED 00 05`인가, 단순히 문자열 `rO0AB`가 포함된 것인가?
- 서명/HMAC을 변조하면 역직렬화 전에 거부되는가?
- `ObjectInputStream` 호출이 외부 입력 경로에 실제로 도달하는가?
- 대상 Java 버전·모듈 제한·클래스패스가 선택한 가젯과 일치하는가?
- URLDNS 질의만으로 Commons Collections RCE가 된다고 보고하지 않았는가?

### 조치

외부 경계에서는 JSON처럼 데이터 타입이 제한된 포맷과 명시적 DTO를 사용합니다. 레거시 호환 때문에 Java 직렬화를 유지하면 서명 검증을 **역직렬화 전에** 하고, JEP 290 필터를 닫힌 허용 목록으로 적용합니다.

```java
ObjectInputFilter filter = ObjectInputFilter.Config.createFilter(
    "maxdepth=8;maxrefs=1000;maxbytes=65536;com.example.dto.*;java.base/java.lang.*;!*"
);
try (ObjectInputStream in = new ObjectInputStream(inputStream)) {
    in.setObjectInputFilter(filter);
    Object value = in.readObject();
}
```

필터는 마이그레이션 보조 수단입니다. 허용 클래스의 자체 `readObject()`가 위험하면 허용 목록만으로 안전해지지 않습니다.

### 탐지 포인트·출처

`ObjectInputStream.readObject` 사용 지점을 SAST로 찾고, 외부 입력과 연결된 호출을 우선 검토합니다. 런타임에서는 역직렬화 필터 거부, 예상 밖 클래스명, 역직렬화 직후 DNS 질의·자식 프로세스 생성을 연계합니다.

- [Oracle — Serialization Filtering](https://docs.oracle.com/en/java/javase/17/core/serialization-filtering1.html)
- [ysoserial](https://github.com/frohoff/ysoserial)
- [PortSwigger — Insecure deserialization](https://portswigger.net/web-security/deserialization)

## 2. PHP — `unserialize()`, POP 체인, `phar://`

### 원리·단서 기능·성립 조건

PHP 직렬화 문자열은 타입과 길이를 함께 담습니다. `O:4:"User":1:{...}`에서 숫자 길이를 임의로 바꾸면 파싱 오류가 나므로, 단순 텍스트 치환 때 길이도 맞아야 합니다. 객체 복원 중 `__unserialize()`·`__wakeup()`, 요청 종료나 객체 소멸 때 `__destruct()`, 문자열 변환 때 `__toString()` 같은 매직 메서드가 호출됩니다. 이미 존재하는 클래스들의 속성을 이어 파일 삭제·템플릿 호출 등으로 연결한 것이 PHP POP(Property-Oriented Programming) 체인입니다.

`phar://`는 파일 연산이 Phar 아카이브를 열게 하는 스트림 래퍼입니다. 과거 PHP에서는 Phar 메타데이터의 객체 역직렬화가 파일 함수에서 간접 트리거될 수 있었습니다. **현대 PHP 버전과 실제 함수·라이브러리 조합에 따라 동작이 달라지므로**, 업로드와 `phar://` 문자열만 보고 취약하다고 판정하지 않습니다.

### 따라하기 A — PortSwigger `Arbitrary object injection in PHP`

- 랩: [Arbitrary object injection in PHP](https://portswigger.net/web-security/deserialization/exploiting/lab-deserialization-arbitrary-object-injection-in-php)
- 로그인 후 Base64 쿠키를 디코딩해 PHP 객체 표식과 속성을 확인합니다.
- 공식 절차에서 노출된 소스의 매직 메서드와 제어 가능한 속성을 추적해 랩이 지정한 객체만 주입합니다.
- 성공 기준은 랩 배너 완료이며, 500 오류나 객체 문자열 반사만으로 성공이라 하지 않습니다.

### 따라하기 B — PortSwigger `Exploiting PHP deserialization with a pre-built gadget chain`

- 랩: [Exploiting PHP deserialization with a pre-built gadget chain](https://portswigger.net/web-security/deserialization/exploiting/lab-deserialization-exploiting-php-deserialization-with-a-pre-built-gadget-chain)
- 오류·소스 단서로 프레임워크와 서명 방식을 식별한 뒤, 공식 절차의 PHPGGC 체인과 랩에서 얻은 키를 사용합니다.
- 체인은 패키지 이름뿐 아니라 **정확한 버전과 클래스 로딩 상태**가 맞아야 합니다.

### 따라하기 C — PortSwigger `Using PHAR deserialization to deploy a custom gadget chain`

- 랩: [Using PHAR deserialization to deploy a custom gadget chain](https://portswigger.net/web-security/deserialization/exploiting/lab-deserialization-using-phar-deserialization-to-deploy-a-custom-gadget-chain)
- 제공 계정으로 로그인한 뒤 정상 JPG 업로드와 `/cgi-bin/avatar.php?avatar=wiener` 요청을 먼저 기록합니다.
- 공식 랩 절차대로 백업 소스에서 `Blog`와 `CustomTemplate`의 속성 흐름, `file_exists()` 도달 지점을 확인하고 Academy가 제공한 PHAR-JPG만 업로드합니다.
- 업로드한 자기 아바타를 `GET /cgi-bin/avatar.php?avatar=phar://wiener`로 읽습니다.

성공 기준은 랩 배너의 완료 표시입니다. 이 랩은 PHAR 메타데이터 역직렬화뿐 아니라 업로드, 커스텀 POP 체인, Twig 호출 조건까지 모두 맞아야 하므로 `phar://` 문자열이 허용된다는 사실만으로 취약하다고 판정하지 않습니다. 개인 Academy 인스턴스는 직접 완료하지 못했고, 랩 이름·URL·절차는 공식 페이지에서 확인했습니다.

### 진단 체크리스트와 오탐 구분

- `unserialize($input, ['allowed_classes' => false])`인지, 객체가 실제 필요한가?
- 매직 메서드가 존재하고 공격자가 필요한 속성을 모두 제어할 수 있는가?
- Composer `vendor/`의 실제 버전이 도구의 체인 요구 조건과 같은가?
- 쿠키 서명이 있으며 키가 안전하게 관리되는가? 유효 서명을 만들 수 없는 변조는 역직렬화 전에 거부되는가?
- 업로드 가능하다는 사실과 `phar://` 경로를 서버가 실제 소비한다는 사실을 분리했는가?

### 조치

```php
// 안전한 경계: JSON을 스키마에 맞는 배열로만 처리한다.
$data = json_decode($raw, true, flags: JSON_THROW_ON_ERROR);
if (!is_array($data) || !isset($data['userId']) || !is_int($data['userId'])) {
    throw new InvalidArgumentException('invalid payload');
}

// 레거시 전환기: 객체 생성을 막아도 장기적으로 JSON으로 제거한다.
$legacy = unserialize($raw, ['allowed_classes' => false]);
```

서명은 비밀 키로 HMAC을 사용하고 `hash_equals()`로 검증한 뒤 역직렬화합니다. 서명이 위험한 포맷 자체를 안전하게 바꾸지는 않으며, 키 노출·재사용 시 방어가 사라집니다.

### 탐지 포인트·출처

외부 입력에서 `unserialize()`, Phar 스트림, 매직 메서드로 이어지는 데이터 흐름을 찾습니다. 로그에서는 `unserialize(): Error at offset`, 예상 밖 클래스명, `phar://` 경로, 역직렬화 직후 파일·프로세스 이벤트를 탐지합니다.

- [PHP manual — unserialize](https://www.php.net/manual/en/function.unserialize.php)
- [PHP manual — Phar metadata](https://www.php.net/manual/en/phar.getmetadata.php)
- [PHPGGC](https://github.com/ambionics/phpggc)

## 3. Python `pickle`과 PyYAML — 데이터 파일처럼 보이는 코드 경로

### 원리·단서 기능·성립 조건

`pickle`은 객체 복원을 위해 callable과 인자를 표현할 수 있습니다. 따라서 제한 없는 `pickle.loads()`는 “파싱”이 아니라 프로그램 실행 권한을 입력에 주는 것과 같습니다. 확장자나 Base64 여부는 방어가 아닙니다.

PyYAML은 로더에 따라 의미가 다릅니다. `yaml.safe_load()`는 기본 YAML 타입만 허용하지만, `yaml.load(..., Loader=yaml.UnsafeLoader)`는 `!!python/object/apply` 같은 Python 전용 태그로 함수를 호출할 수 있습니다. `FullLoader`·`UnsafeLoader`·버전별 기본값을 혼동하지 말고 실제 호출을 확인합니다.

### 따라하기 — localhost Docker

파일 세 개를 빈 폴더에 저장합니다.

`compose.yaml`

```yaml
services:
  python-lab:
    build: .
    ports:
      - "127.0.0.1:18181:8080"
```

`Dockerfile`

```dockerfile
FROM ghcr.io/astral-sh/uv:python3.13-alpine
RUN uv pip install --system PyYAML==6.0.3
WORKDIR /lab
COPY app.py /lab/app.py
CMD ["python", "/lab/app.py"]
```

`app.py`

```python
import base64
import pickle
from http.server import BaseHTTPRequestHandler, HTTPServer

import yaml


class Handler(BaseHTTPRequestHandler):
    def reply(self, status: int, text: str) -> None:
        data = text.encode()
        self.send_response(status)
        self.send_header("Content-Type", "text/plain; charset=utf-8")
        self.send_header("Content-Length", str(len(data)))
        self.end_headers()
        self.wfile.write(data)

    def do_POST(self) -> None:
        body = self.rfile.read(int(self.headers.get("Content-Length", "0")))
        try:
            if self.path == "/pickle":
                value = pickle.loads(base64.b64decode(body))
            elif self.path == "/yaml-unsafe":
                value = yaml.load(body, Loader=yaml.UnsafeLoader)
            elif self.path == "/yaml-safe":
                value = yaml.safe_load(body)
            else:
                self.reply(404, "not found\n")
                return
            self.reply(200, f"type={type(value).__name__} value={value!r}\n")
        except Exception as error:
            self.reply(400, f"rejected={type(error).__name__}\n")


HTTPServer(("0.0.0.0", 8080), Handler).serve_forever()
```

```bash
docker compose up --build -d

# 무해한 pickle 정수 42: gAVLKi4= 는 격리 앱에서만 사용
printf 'gAVLKi4=' | curl -s --data-binary @- http://127.0.0.1:18181/pickle
# 기대: type=int value=42

# unsafe loader는 Python callable을 실행해 현재 디렉터리를 반환
printf '!!python/object/apply:os.getcwd []' | curl -s --data-binary @- http://127.0.0.1:18181/yaml-unsafe
# 기대: type=str value='/lab'

# 동일 입력을 safe loader가 거부
printf '!!python/object/apply:os.getcwd []' | curl -s --data-binary @- http://127.0.0.1:18181/yaml-safe
# 기대: rejected=ConstructorError
```

## 4. .NET — `BinaryFormatter`와 ViewState MAC을 분리해서 보기

### 원리·단서 기능·성립 조건

`BinaryFormatter`는 입력이 타입을 지정하고 객체 그래프를 구성하게 하므로 안전하게 만들 수 없습니다. `SerializationBinder`는 알려진 타입을 줄일 수 있어도 DoS와 미래 우회를 제거하지 못합니다. .NET 9부터 인박스 구현은 사용 시 예외를 던지므로, 현대 런타임에서 `BinaryFormatter` 문자열을 찾았다는 사실만으로 도달 가능한 취약점이라 하지 않습니다. 레거시 .NET Framework, 호환 패키지, `LosFormatter`·`ObjectStateFormatter` 같은 관련 포맷을 함께 봅니다.

ASP.NET ViewState는 페이지 상태 직렬화 형식입니다. `__VIEWSTATE`가 있다는 것 자체는 정상이며, 기본적으로 MAC이 유효하면 임의 변조가 거부됩니다. 공격이 성립하려면 MAC 비활성화, 노출·재사용된 정적 `machineKey`, 잘못된 validation 설정처럼 **공격자가 유효한 무결성 값을 만들 조건**이 필요합니다. 암호화 여부와 MAC 여부도 별개입니다.

### 따라하기 — localhost 정적 식별과 변조 거부 확인

허가된 로컬 ASP.NET 테스트 앱에서 정상 페이지를 두 번 받아 `__VIEWSTATE`와 `__VIEWSTATEGENERATOR`를 저장합니다. 한 글자만 바꾼 ViewState를 같은 페이지·세션에 다시 POST합니다.

```http
POST /Form.aspx HTTP/1.1
Host: 127.0.0.1
Content-Type: application/x-www-form-urlencoded

__VIEWSTATE=%2FwEP...A&__VIEWSTATEGENERATOR=CA0B0334&submit=1
```

성공적인 **방어 확인**은 변조본이 ViewState MAC validation 오류로 거부되고 상태 변경이 일어나지 않는 것입니다. 정상 ViewState가 Base64라는 사실, 500 오류 한 번, 공개된 `__VIEWSTATEGENERATOR`만으로 키 노출이나 RCE라고 판정하지 않습니다. `BinaryFormatter`는 .NET 8 이하의 격리된 레거시 복제 환경에서만 코드 경로를 검토하며, 공개 서비스에 ysoserial.net 페이로드를 보내지 않습니다.

### 진단 체크리스트와 오탐 구분

- 정확한 런타임과 앱 설정에서 위험 deserializer 호출이 가능한가?
- 외부 입력이 서명 검증 전에 deserializer에 도달하는가?
- ViewState MAC이 실제로 비활성인가, 단지 값이 읽을 수 있는가?
- `machineKey`가 소스·백업·이미지·여러 환경에서 노출 또는 재사용되는가?
- ViewState purpose, virtual path, generator 등 필요한 컨텍스트가 일치하는가?

### 조치

`BinaryFormatter`와 관련 위험 serializer를 제거하고 `System.Text.Json`의 명시적 DTO로 이전합니다. 타입 판별자를 입력이 임의 지정하게 하지 말고 허용된 값과 타입을 코드에서 매핑합니다. ViewState MAC을 끄지 말고 자동 생성된 고유 키 또는 안전한 키 저장소를 사용하며, 환경 간 키 재사용과 저장소 커밋을 금지합니다.

```csharp
public sealed record SessionState(int UserId, string Theme);

SessionState? state = JsonSerializer.Deserialize<SessionState>(json);
if (state is null || state.UserId <= 0) {
    throw new JsonException("invalid state");
}
```

### 탐지 포인트·출처

CA2300 계열 분석 규칙, `BinaryFormatter.Deserialize`, `LosFormatter.Deserialize`, `ObjectStateFormatter.Deserialize` 호출을 CI에서 차단합니다. 운영 로그에서는 ViewState MAC validation 실패 급증, 비정상적으로 큰 ViewState, 역직렬화 직후 프로세스 생성을 연계합니다.

- [Microsoft — BinaryFormatter security guide](https://learn.microsoft.com/en-us/dotnet/standard/serialization/binaryformatter-security-guide)
- [Microsoft — BinaryFormatter migration guide](https://learn.microsoft.com/en-us/dotnet/standard/serialization/binaryformatter-migration-guide/)
- [Microsoft — ASP.NET View State overview](https://learn.microsoft.com/en-us/previous-versions/aspnet/bb386448(v=vs.100))

## 5. Node.js `node-serialize` — 함수 문자열이 복원될 때

### 원리·단서 기능·성립 조건

과거 `node-serialize`는 `_$$ND_FUNC$$_` 접두사가 붙은 문자열을 함수로 복원했습니다. 함수 문자열 끝에 호출 형태가 붙고 비신뢰 쿠키·본문이 `unserialize()`에 들어가면 서버 권한의 JavaScript가 실행될 수 있습니다. 이 표식은 JavaScript 표준 직렬화가 아니며, 패키지가 설치되어 실제 취약 경로가 호출되어야 합니다.

### 따라하기 — localhost Docker

`compose.yaml`

```yaml
services:
  node-lab:
    build: .
    ports:
      - "127.0.0.1:18282:8080"
```

`Dockerfile`

```dockerfile
FROM node:22-alpine
WORKDIR /lab
RUN npm install --omit=dev node-serialize@0.0.4
COPY server.js /lab/server.js
CMD ["node", "/lab/server.js"]
```

`server.js`

```javascript
const http = require("http");
const serialize = require("node-serialize");

http.createServer((request, response) => {
  const chunks = [];
  request.on("data", (chunk) => chunks.push(chunk));
  request.on("end", () => {
    try {
      const value = serialize.unserialize(Buffer.concat(chunks).toString("utf8"));
      response.writeHead(200, {"Content-Type": "text/plain"});
      response.end(`value=${String(value.proof)}\n`);
    } catch (error) {
      response.writeHead(400, {"Content-Type": "text/plain"});
      response.end(`rejected=${error.name}\n`);
    }
  });
}).listen(8080, "0.0.0.0");
```

```bash
docker compose up --build -d
printf '%s' '{"proof":"_$$ND_FUNC$$_function(){return 6*7}()"}' \
  | curl -s --data-binary @- http://127.0.0.1:18282/
# 기대: value=42
```

> [!success] 직접 검증
> 2026-11-27에 `node-serialize@0.0.4` 컨테이너를 빌드하고 함수가 `42`로 평가되는 것을 확인했습니다. 파일·프로세스·네트워크 접근은 사용하지 않았습니다.

### 진단 체크리스트와 오탐 구분

- `package-lock.json`과 실제 배포 이미지에 `node-serialize`가 존재하는가?
- 외부 입력이 `unserialize()`까지 도달하며 앞서 HMAC 검증되는가?
- `_$$ND_FUNC$$_`가 단순 로그·문자열로 저장되는 것이 아니라 함수로 복원되는가?
- 테스트는 계산식처럼 비파괴 증거로 멈췄는가?

### 조치·탐지 포인트·출처

패키지를 제거하고 `JSON.parse()` 후 JSON Schema로 키·타입·길이·추가 속성을 검증합니다. 함수·클래스 인스턴스를 클라이언트 상태로 보내지 않습니다. 의존성 스캔에서 폐기 패키지를 차단하고, 요청에 `_$$ND_FUNC$$_`가 나타나거나 Node 웹 프로세스가 예기치 않은 자식 프로세스를 만들면 경보합니다.

- [node-serialize package](https://www.npmjs.com/package/node-serialize)
- [CWE-502 — Deserialization of Untrusted Data](https://cwe.mitre.org/data/definitions/502.html)

## 6. 공통 조치 — 허용 목록과 서명의 정확한 위치

1. **포맷 제거**: 외부 신뢰 경계에서 네이티브 객체 그래프를 없애고 JSON/Protobuf의 명시적 메시지로 바꿉니다.
2. **스키마 허용 목록**: 타입명 문자열을 입력에서 받아 동적 로딩하지 않습니다. 필드·타입·길이·중첩 깊이·전체 크기를 제한합니다.
3. **서명 먼저**: `HMAC(key, version || payload)`를 상수 시간 비교로 검증한 뒤에만 파싱합니다. 암호화만으로 무결성이 생기지 않습니다.
4. **키 수명주기**: 키를 코드·이미지·클라이언트에 넣지 않고 환경별로 분리하며 회전 버전을 둡니다.
5. **격리와 최소 권한**: 마이그레이션 중 레거시 파서는 별도 저권한 프로세스, egress 차단, CPU·메모리·깊이 제한 안에서 실행합니다.

서명이 있으면 임의 변조를 막을 수 있지만, 합법적으로 서명된 오래된 악성 객체, 키 노출, 서명 전에 파싱하는 순서 오류는 막지 못합니다. 허용 목록도 허용된 클래스 자체의 부작용과 자원 고갈을 자동 해결하지 않습니다.

## 다음 단계로 이어지는 공격

역직렬화에서 얻은 코드 실행은 애플리케이션 계정의 파일·환경 변수·DB 자격증명 접근으로 이어지고, DNS/HTTP 가젯만 성립해도 내부망 도달성이나 데이터 유출 채널의 단서가 됩니다. 세션 객체 속성만 변조 가능한 경우에는 관리자 플래그·객체 ID 조작을 통한 인증·인가 우회로 이어질 수 있으므로, **탐지된 primitive와 실제 가젯 조건을 분리해** 다음 공격 단계를 평가합니다.
