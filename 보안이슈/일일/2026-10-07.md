## 2. 이슈별 분석

### [D20261007-bitget] Bitget 가상자산 탈취 (보안 제품 제로데이)
> 날짜: 2026-09-25 · 유형: 서드파티 보안 제품 제로데이 → 내부 이동 → 지갑 서버 · 행위자: 미귀속(회사는 북한 해커 주장, 미검증) · 지역: 글로벌 · 근거: 보도

**쉽게 말하면**: 가상자산 거래소 Bitget이 약 3억 8,750만 달러어치 자산을 도난당했다고 밝혔습니다. 회사 설명에 따르면 외부 보안 제품의 제조사도 모르던 결함이 공격에 쓰였고, 그 제품 장비들이 입구가 됐고, 그곳에서 지갑을 관리하는 서버까지 들어갔다고 합니다. 어떤 제품인지는 공개되지 않았고, 누구 소행인지도 확정되지 않았습니다.

**먼저 할 일(초보용)**: 이용자는 거래소 공지를 확인하고 출금 재개 전까지 공식 안내 외의 '복구 도와드립니다' 연락을 믿지 마세요. 담당자라면 인터넷에 노출된 보안 장비의 버전과 관리 화면 노출을 점검하고, 의심 장비에서 새 키·비밀번호를 만들지 말고 깨끗한 기기에서 교체하세요.

**개요**: 회사 발표를 전한 보도(9/30) 기준, 가장 이른 악성 활동은 8/31이고 실제 탈취는 9/25(UTC+8) 약 3시간 동안 이뤄졌다. ETH·XRP·BNB·AVAX·USDT·USDC 등 여러 블록체인의 자산이 대상이다. 회사는 출금을 중단하고 회수 협조에 5% 현상금을 내걸었다. CVE 번호와 제품명은 공개되지 않았다(1차 발표 원문은 직접 확인하지 못함).

**왜 일어났나**
- 직접 원인 [보도: 회사 설명]: 서드파티 보안 제품의 제로데이 악용 후 장비 두 대(A·B)가 침해됐다는 설명 → 웹셸 설치와 C2(공격자 원격 조종) 연결 → 지갑 서버로 이동 → 악성 패키지 배포로 지갑 처리 과정에서 자산을 이전(위조 출금 명령 주입 등 세부 방식은 확인 필요). 각 단계의 기술적 증거는 공개되지 않았다.
- 구조적 원인 [추정]: (1) 보안 제품이 공격 입구가 됨(인터넷에 노출된 서비스였는지는 미확인) (2) 보도된 최초 악성 활동(8/31)부터 자산 이전(9/25)까지 약 25일이 걸렸으나 최초 침투·탐지·대응 시점은 별도 확인이 필요함(미탐지로 단정하지 않음) (3) 일반 서버 대역에서 핫월렛(즉시 이체 가능한 지갑) 서버로 이어지는 경로 분리 미흡 가능성. 이는 본 보고서의 분석이며 확인된 사실이 아니다.
- 배후 [주장]: 대표가 접속 패턴과 블록체인 분석을 근거로 북한을 지목했으나 외부 연구자의 독립 검증은 없다.

**침투 경로 [보도: 회사 설명 인용]**: 보안 제품 제로데이 → 웹셸·C2 → 내부 이동 → 운영 지갑 서버 → 악성 패키지 → 자산 이체. 내부 이동의 구체 수단은 미공개.

**어떻게 조치하나**
- 즉시: 증거 보존 후 해당 계열 보안 장비의 패치·우회책 적용, 관리 화면 외부 차단. 침해 의심 장비는 재구축하고 그 장비를 거친 키·인증서는 폐기 후 깨끗한 환경에서 재발급.
- 단기: 장비 로그에서 웹셸·비정상 아웃바운드 점검, 지갑 서버로 가는 접속 경로 전수 확인, 대량 출금 한도·지연·다중 승인.
- 장기: 지갑 서명 키를 하드웨어 보관(HSM 등)·다중 서명으로 분리, 보안 장비 관리면 분리, 엣지 장비 긴급 패치 기준.
- 탐지: 장비의 신규 파일·비정상 프로세스, 지갑 서버로의 새 접속원, 평소와 다른 배포 활동.

**교훈**: 보안 장비도 공격 입구가 된다. 최초 활동에서 탈취까지 약 25일이 걸렸으니 그 사이 탐지 기회가 있었는지 점검할 만하다(탐지 실패를 단정하는 것은 아니다).

### [D20261007-roundcube] Roundcube 웹메일 CVE-2026-48842 악용
> 날짜: 2026-09-21 · 유형: 엣지·웹 서비스 취약점 · 행위자: 미귀속 · 지역: 글로벌 · 근거: 보도

**쉽게 말하면**: 웹으로 메일을 보는 프로그램(Roundcube)에서 로그인 없이도 데이터베이스에 명령을 끼워 넣을 수 있는 결함이 5월에 패치됐는데, 아직 안 고친 서버를 노린 공격이 벌어지고 있다고 캐나다 정부 기관이 공개 보고를 인용해 경고했습니다. 약 52만 대가 인터넷에 노출돼 있다고 보도됐습니다.

**먼저 할 일(초보용)**: 메일 서버 담당자는 Roundcube 버전을 확인하고 1.6.16 또는 1.7.1 이상(당시 기준)으로 올리세요. 이미 뚫렸을 수 있으니 패치만으로 끝내지 말고 접속 기록과 사용자 계정 이상 여부를 보세요.

**개요**: Roundcube의 `virtuser_query` 플러그인에서 인증 없이 가능한 SQL 삽입이다. 캐나다 사이버보안센터가 9/21 갱신된 공지에서 "공개 보고가 실제 악용을 나타낸다"고 밝혔다(센터가 직접 검증했다는 뜻은 아님; 개발사는 5/24 패치 공지). 심각도는 '높음'(점수 미확인). CISA KEV 등재 여부는 이번 확인에서 알 수 없었다(KEV 목록 상위 15건에는 없음).

**왜 일어났나**
- 직접 원인 [확인: 개발사 공지]: `virtuser_query` 플러그인의 입력 검증 결함. 5월에 수정본이 나왔다.
- 구조적 원인 [추정]: (1) 패치가 나온 지 4개월이 지나도 많은 서버가 미적용 (2) 메일 서버가 인터넷에 직접 노출. 구체적 피해 사례와 공격자 목적은 공개되지 않았다.

**침투 경로 [보도 범위]**: 인터넷 노출 Roundcube에 조작 요청 → 인증 우회·DB 명령 실행. 이후 행위는 미공개.

**어떻게 조치하나**
- 즉시: 증거 보존 후 수정 버전 적용(패치를 미루지 않음).
- 단기: 웹서버·DB 로그에서 `virtuser_query` 관련 비정상 요청 소급 점검, 메일함 접근·전달 규칙 이상 확인, 의심 시 DB 자격 증명을 깨끗한 기기에서 교체.
- 장기: 웹메일 접근 IP 제한·VPN 뒤 배치, 소프트웨어 자산 목록과 자동 패치 점검.
- 탐지: 웹 로그의 SQL 구문 문자열, 비정상 DB 질의량.

**교훈**: 패치가 나온 뒤에도 몇 달 지나 공격이 시작될 수 있다. 오래된 공개 취약점이 가장 흔한 입구다.

### [D20261007-asos] ASOS 침해 주장과 인정된 개인정보 유출
> 날짜: 2026-10-06 · 유형: 서드파티 플랫폼 무단 접근 · 행위자: 'Xuanye group' 자칭 · 지역: 글로벌 · 근거: 보도

**쉽게 말하면**: 영국 온라인 패션몰 ASOS 앱에서 "해킹당했다"는 알림이 이용자에게 전송됐습니다. 회사는 고객 소통에 쓰는 외부 플랫폼에 무단 접근이 있었고 이름·연락처 같은 기본 정보가 접근됐을 가능성이 있다고 밝혔습니다. 다만 공격자가 주장한 '데이터 저장소(Snowflake) 완전 장악'은 확인되지 않았습니다.

**먼저 할 일(초보용)**: 이용자는 ASOS를 사칭한 문자·이메일(링크 클릭 유도)을 조심하세요. 회사 발표에 따르면 회사는 카드 정보·비밀번호가 영향받지 않은 것으로 판단한다고 하지만, 앱 알림 속 링크는 누르지 마세요. 담당자는 외부 고객 소통 플랫폼의 계정·토큰 접근을 점검하세요.

**개요**: 10/6 ASOS 앱 푸시 알림으로 알려졌다. 자칭 'Xuanye group'이 텔레그램에서 책임을 주장했다. 영향 고객 수와 유출 범위, 공격 방법은 미확인이다(BleepingComputer 보도 한 건 기준). 서드파티 플랫폼 무단 접근은 회사 확인, Snowflake 장악은 공격자 주장이다.

**왜 일어났나**
- 직접 원인 [보도: 회사 확인]: 고객 소통용 서드파티 플랫폼에 무단 접근. 접근 방법(탈취한 자격 증명인지 취약점인지)은 **확인되지 않았다**.
- 구조적 원인 [추정]: 외부 서비스가 고객 알림 발송 권한까지 가진 구조는 한 곳이 뚫리면 이용자에게 직접 영향이 간다. 이 건의 실제 원인으로 단정하지 않는다.
- Snowflake 장악 [주장: 공격자]: 증거가 제시되지 않았다.

**침투 경로**: 미공개 (공격자 주장 외 확인된 경로 없음). 그래서 ATT&CK 매핑은 하지 않았다.

**어떻게 조치하나**
- 즉시: 증거 보존, 서드파티 플랫폼의 API 키·세션 토큰 회수(비밀번호 변경만으로는 이미 발급된 토큰이 사라지지 않음), 알림 발송 권한 임시 차단.
- 단기: 연동 서비스별 권한·접속 기록 점검, 데이터 저장소 접근 로그 확인.
- 장기: 외부 서비스에 최소 권한, 키 주기적 교체, 서드파티 접근 이상 탐지.
- 탐지: 평소와 다른 알림 발송, 외부 서비스의 새 접속원.

**교훈**: 공격자의 큰 주장과 회사가 확인한 범위는 다르다. 확인된 것만 믿고 대응하되, 서드파티 연동 권한은 평소에 줄여 두어야 한다.

## 5. 우선 대응 체크리스트

4. **외부 플랫폼 연동**: 토큰·API 키 목록과 권한 점검.

## 6. 검증 수준과 한계

- Bitget은 BleepingComputer 보도(회사 발표 인용) 한 건에 근거하며 회사 원문·제품명·CVE는 확인하지 못했다. 북한 배후는 회사 주장이다.
- Roundcube의 악용은 캐나다 사이버보안센터 공지(원문 확인: "공개 보고가 악용을 나타낸다")에 근거하며 센터의 직접 검증은 아니다. 구체적 피해 사례는 확인하지 못했다.
- ASOS는 BleepingComputer 한 건 기준이며 규모는 미확인이다. 공격자 주장은 사실로 취급하지 않았다.
- 국내: 금융권·통신·공공·랜섬웨어 질의를 했으나 10/6~7 신규 대형 사건은 확인하지 못했다. 금융위가 10/7 금융사 자체 점검 결과를 놓고 추가 회의를 연다는 보도와 금융당국의 점검 체크리스트·금감원 검사 방침만 국내뉴스에 추가했다. 검색에 나온 병원·대학 사례는 발생 시점을 확인하지 못해 제외했다.
- Citrix·FortiMail 후속과 9/24~25 KEV(SharePoint·MikroTik·Adobe Magento·WSO2·Check Point)는 분석하지 못했다.
- ATT&CK는 v19.2 기준이다(공식 사이트 점검 결과는 최종 요약 참고).
