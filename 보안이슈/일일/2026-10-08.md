### [D20261008-atlassian] Atlassian 제품군 CVE-2026-21589 악용
> 날짜: 2026-10-07 · 유형: 엣지·웹 서비스 취약점 · 행위자: 미귀속 · 지역: 글로벌 · 근거: 보도

**쉽게 말하면**: 회사 안에 직접 설치해 쓰는 업무 도구(Jira, Confluence, Bitbucket 등)에서 로그인 없이 서버의 파일을 읽을 수 있는 결함이 발견됐고, 연구기관이 공격 방법을 공개한 지 약 2시간 만에 공격 시도가 관측됐다고 보도됐습니다. 자동 검사 도구까지 퍼져 있어 노출된 서버는 금방 표적이 될 수 있습니다.

**먼저 할 일(초보용)**: 담당자는 직접 설치형 Atlassian 제품의 버전을 확인하고 Atlassian 공식 보안 공지의 수정 버전으로 올리세요. 인터넷에서 바로 접근되지 않게 막고, 이미 공격받았을 수 있으니 패치 후에도 접속 기록과 설정 파일·비밀 값 노출 여부를 점검하세요.

**개요**: BleepingComputer(10/7) 보도에 따르면 CVE-2026-21589는 Bitbucket·Confluence·Jira Software·Jira Service Management·Bamboo·Crowd Data Center와 Crucible·Fisheye의 자체 설치형 인스턴스에서 인증 없이 웹 애플리케이션 안의 파일에 접근할 수 있는 결함이다(보도는 '임의 파일'로 표현했으나 정확한 경로가 필요한 등 범위 조건은 Atlassian 공지에서 확인해야 한다). 보안업체 Previdian이 허니팟(미끼 서버)으로 공격을 탐지했고 watchTowr가 기술 분석과 공개 시연 코드(PoC)를 냈다. 수정 버전은 보도에 없어 Atlassian 공지를 확인해야 한다(원문 공지는 직접 확인하지 못함). CISA KEV 등재는 아직 없다.

**왜 일어났나**
- 직접 원인 [보도]: 인증 없이 파일 경로를 조작해 파일을 읽을 수 있는 구현상 결함(세부 원인은 공지 확인 필요).
- 구조적 원인 [추정]: (1) 공개 시연 코드가 나오면 수 시간 안에 악용이 시작되는 속도 (2) 업무 도구가 인터넷에 직접 노출되는 운영 (3) 소스·티켓 도구에 설정 파일과 비밀 값이 모여 있어 파일 읽기만으로 이후 침투로 이어질 수 있음. 이는 분석이며 확인된 사실이 아니다.

**침투 경로 [보도 범위]**: 인터넷 노출 인스턴스에 조작된 요청 → 임의 파일 읽기. 이후 행위(자격 증명 탈취 등)는 확인되지 않았다.

**어떻게 조치하나**
- 즉시: 증거 보존 후 수정 버전 적용(패치를 미루지 않음). 패치 전에는 외부 접근 차단, WAF·프록시로 경로 조작 패턴 차단, 제품별 임시 완화 규칙(보도에 소개된 Tomcat 재작성 규칙 등)은 공지에서 확인해 적용.
- 단기: 웹 로그에서 경로 조작 요청과 보도된 의심 IP(38.60.157.86, 146.70.187.234, 159.26.119.225 — 보도 기준) 접속 소급 점검. 서버에 저장된 DB 접속 정보·토큰·연동 키 노출 가능성을 따져 깨끗한 기기에서 교체(비밀번호만 바꾸면 이미 발급된 토큰은 남음).
- 장기: 관리용 협업 도구는 VPN 뒤에 두기, 자산 목록과 긴급 패치 기준 마련.
- 탐지: 설정·키 파일에 대한 비정상 읽기, 새로 생긴 관리자·API 토큰.

**교훈**: 공개 시연 코드와 자동 검사 템플릿이 함께 나오면 패치 여유 시간은 사실상 없다.

### [D20261008-fortibleed] FortiBleed — 유출된 FortiGate 로그인 정보의 랜섬웨어 악용
> 날짜: 2026-10-07 · 유형: 유출 자격 증명 재사용 · 행위자: INC/Lynx·Payload 랜섬웨어 계열이 연루됐다고 FBI가 경고(보도) · 지역: 글로벌 · 근거: 보도

**쉽게 말하면**: 방화벽·VPN 장비(FortiGate)의 아이디와 비밀번호 묶음이 유출돼 돌아다니고 있고, 이를 이용한 침입이 계속되고 있다고 FBI가 경고했다고 보도됐습니다. 침입자는 관리자 계정을 새로 만들고 기존 관리자를 지워 원래 담당자를 쫓아냈습니다. 특정 제품 결함이 아니라 유출된 로그인 정보를 쓰는 공격이라는 점이 핵심입니다.

**먼저 할 일(초보용)**: 담당자는 FortiGate 관리 화면과 SSL VPN이 인터넷에 열려 있는지 확인하고 막으세요. 장비 안의 관리자 목록과 최근 설정 변경에서 낯선 계정을 찾으세요. 침입이 의심되면 그 장비에서 새 비밀번호를 만들지 말고 깨끗한 기기에서 바꾸며, 이미 열린 VPN 접속(세션)도 모두 끊어야 합니다.

**개요**: BleepingComputer(10/7) 보도에 따르면 'FortiBleed'는 194개국 86,644대 기기의 접속 정보(아이디·평문 비밀번호)가 유출된 사건의 이름이다(규모는 보도 기준이며 단위는 기기. 최초 유출 자료의 계정 수와 후속 침해 장비 집계가 섞였을 수 있어 모집단은 불명확). FBI는 이 공격 흐름이(관리자 계정 생성·삭제는 일부 사고에서 관측) 랜섬웨어 제휴자(INC/Lynx, Payload)의 첫 진입점으로 관측됐다고 밝힌 것으로 보도됐다. 특정 CVE나 취약 버전은 보도에 없다. 정보 탈취 악성코드 기록·크리덴셜 스터핑·비밀번호 스프레이로 계정을 얻고, 장비에서 비밀번호 해시를 꺼내 GPU 군집으로 오프라인 해독한다고 한다. FBI 원문은 직접 확인하지 못했다.

**왜 일어났나**
- 직접 원인 [보도: FBI 인용]: 유출·재사용된 로그인 정보와 약한 비밀번호 저장 방식(과거 방식 해시)으로 인한 장비 접근.
- 구조적 원인 [추정]: (1) 관리·VPN 화면의 인터넷 노출 (2) MFA 미적용 계정 (3) 유출 목록을 받아 교체하지 않는 운영. 유출 경위 자체는 공개되지 않았다.

**침투 경로 [보도: FBI 인용]**: 유출·탈취 자격 증명 → 방화벽/VPN 로그인 → 관리자 계정 생성·기존 관리자 삭제(접근 차단) → 랜섬웨어 단계로 이어짐.

**어떻게 조치하나**
- 즉시: 증거(장비 로그·설정 백업) 보존 후 관리 화면·SSL VPN 외부 접근 제한, 활성 VPN 세션 종료, 관리자·VPN 계정 비밀번호를 깨끗한 기기에서 교체하고 MFA 강제. 비밀번호만 바꿔서는 이미 발급된 세션이 사라지지 않으므로 세션 종료를 따로 한다.
- 단기: 관리자 목록·설정 변경 이력에서 낯선 계정 점검·제거, 내부 이동 흔적 조사, 장비 설정에 저장된 비밀(연동 계정 등) 교체, 의심 장비는 재구축 판단(침해된 장비에서 새 비밀을 발급하지 않음).
- 장기: 관리면 분리, 관리자 비밀번호 저장 방식 강화(보도는 PBKDF2, 지원 버전은 제조사 절차 확인; 이미 탈취된 비밀번호는 별도로 교체해야 함), 유출 목록 모니터링.
- 탐지: 관리자 계정 생성·삭제 로그, 평소와 다른 접속원의 VPN 로그인.

**교훈**: 패치만으로는 막을 수 없는 입구가 있다. 유출된 로그인 정보는 이미 공격자 손에 있다고 보고 교체와 MFA를 해야 한다.

### [D20261008-cctld] 국가 도메인 관련 침해와 구글 도메인 인증서 부정 발급
> 날짜: 2026-10-07 · 유형: 서드파티(도메인 운영 쪽) 침해 → DNS 변조 · 행위자: 미귀속 · 지역: 글로벌 · 근거: 보도

**쉽게 말하면**: 인터넷 주소를 관리하는 일부 나라(가나, 아메리칸사모아, 시에라리온)의 도메인 운영 쪽이 뚫려, 공격자가 주소 안내 정보를 바꾸고 구글 관련 주소에 대한 '정상으로 보이는 보안 인증서'까지 받아 냈다고 구글이 밝혔다고 보도됐습니다. 구글 자체 시스템은 안전하다고 합니다. 가짜 사이트가 진짜처럼 보일 수 있다는 점이 문제입니다.

**먼저 할 일(초보용)**: 일반 이용자는 브라우저를 최신으로 유지하세요(구글은 Chrome에서 해당 인증서를 차단했다고 합니다). 도메인 담당자는 자사 도메인의 인증서 발급 기록을 공개 감시 목록(인증서 투명성 로그)에서 확인하고, 인증서를 발급할 수 있는 기관을 제한하는 CAA 기록을 설정하세요(CAA는 이후 부정 발급을 줄일 뿐 진행 중인 DNS 탈취를 막지는 못합니다).

**개요**: BleepingComputer(10/7)가 구글의 공식 발표를 인용해 보도했다. 공격자는 .gh·.as·.sl 국가 코드 최상위 도메인(ccTLD)의 서드파티 운영자를 침해해 권한 있는 DNS 기록을 수정하고, 인증기관에서 유효한 TLS 인증서를 받았다. 구글은 CRLSet으로 Chrome에서 차단했고, 인증서 투명성 로그에서 찾은 추가 인증서도 선제 차단했다. 구글은 영향 도메인을 모두 찾지 못했을 수 있고 CRLSet 보호는 Chrome 이용자에만 적용된다고 밝혔다. 구글 원문은 직접 확인하지 못했다.

**왜 일어났나**
- 직접 원인 [보도: 구글 발표 인용]: 서드파티 운영자 침해로 DNS 기록 수정 권한을 얻었다. 최초 침투 방법은 **확인되지 않았다**.
- 구조적 원인 [추정]: 인증서 발급이 'DNS를 제어하는 쪽이 도메인 주인'이라는 가정에 의존하므로, 상위 DNS가 뚫리면 정상 발급 절차로 부정 인증서가 나올 수 있다. 이는 분석이다.

**침투 경로 [보도 범위]**: 서드파티 운영자 침해(경위 미공개) → DNS 기록 변조 → 인증서 요청·발급 → 도메인 사칭 가능.

**어떻게 조치하나**
- 즉시: 해당 ccTLD 하위에 도메인이 있으면 증거 보존 후 DNS 기록·위임을 점검해 정상으로 복구하고 레지스트라 계정 점검. Chrome 차단은 다른 브라우저·도메인까지 보호하지 않는다. 부정 발급 인증서는 발급기관에 폐기를 요청.
- 단기: 인증서 투명성 로그 감시를 도메인 전체로 확대, CAA 기록 설정, 레지스트라 계정 MFA.
- 장기: 핵심 도메인은 레지스트리 락과 DNSSEC 적용(적용 가능 여부와 보호 범위는 운영자마다 다르며 운영자 자체 침해까지 막지는 못함), 중요 서비스는 인증서 발급 모니터링.
- 탐지: 투명성 로그에 처음 보는 발급, DNS 응답 변경.

**교훈**: 내 시스템이 안전해도 주소 체계를 맡은 외부가 뚫리면 사칭이 가능하다. 인증서 발급 기록을 감시하는 것이 가장 싼 방어다.

## 3. 교차 분석

> 표본은 3건이며 추세를 말하지 않는다.

1. **속도**: Atlassian은 공개 시연 코드 후 약 2시간 만에 악용이 관측됐다고 보도됐다.
2. **자격 증명**: FortiBleed는 취약점이 아닌 유출 로그인 정보 재사용이다. 패치만으로는 해결되지 않는다.
3. **서드파티·상위 인프라**: ccTLD 건은 자사 밖의 주소 체계가 입구다. 다만 세 건의 직접 연관성은 없다.

## 4. 침투 경로 종합

```
[노출 서비스] → T1190 Atlassian 인증 없는 파일 접근(허니팟에서 관측된 악용 시도 기준)
[유출 자격 증명] → T1110/T1078 FortiGate 로그인 → T1136 관리자 생성 → T1531 관리자 차단
[상위 인프라] → T1584 DNS 운영 쪽 변조 (최초 침투 미공개)
```

## 5. 우선 대응 체크리스트

1. **Atlassian 직접 설치형**: 공지 확인, 수정 버전 적용, 외부 접근 차단.
2. **FortiGate**: 관리면·SSL VPN 외부 접근 제한, 세션 종료, 관리자 목록 점검, MFA.
3. **도메인**: 인증서 투명성 로그 감시와 CAA 설정, 레지스트라 계정 보호.
4. **Citrix(10/7 기한 경과)**: 후속은 [10-06 보고서](2026-10-06.md) 참고.

## 6. 검증 수준과 한계

- 세 건 모두 BleepingComputer 보도 한 건씩에 근거하며 Atlassian 공지·FBI 경고·구글 발표 원문은 직접 확인하지 못했다.
- Atlassian의 수정 버전 번호와 KEV 등재 여부, FortiBleed의 유출 경위와 기기 수 검증, ccTLD 침해의 최초 경로는 확인하지 못했다.
- 보도 속 'FBI 관측'은 BleepingComputer 인용이며 FBI 원문은 보지 못했다. ATT&CK 매핑은 본 보고서 작성자의 판단이다. T1531은 공식 플랫폼 목록에 네트워크 장비가 없을 수 있어 행위 기준으로 매핑했다.
- 국내: 금융·통신·이커머스·공공·교육·의료·랜섬웨어 질의를 했으나 10/7~8 신규 대형 사건과 금융위 10/7 회의 결과 발표는 확인하지 못했다(국내뉴스에 추가한 항목 없음).
- Advantest 랜섬웨어 건은 1차 확인 부족으로 제외했다. 9/22~25 KEV(SharePoint·MikroTik·Magento·WSO2·Check Point)는 분석하지 못했다.
- ATT&CK는 v19.2 기준이다(공식 사이트 점검 결과는 최종 요약 참고).
