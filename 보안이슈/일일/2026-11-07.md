### [D20261110-sshole] 'SSHole' OpenSSH 인증 우회(CVE-2026-123158), musl 기반 리눅스 실제 악용
> 날짜: 결함 발견·수정판(10.6p2) 출시 2026-11-05 · 공격 시도 시작 2026-11-05 · 첫 성공 악용 확인(GreyNoise) 2026-11-07 00:46(UTC) · 유형: 네트워크 노출 서비스(SSH) 인증 우회(실제 악용 확인) · 행위자: 다수(봇넷·암호화폐 채굴 포함, 단일 조직 아님) · 지역: 전 세계(해외) · 근거: 확인(OpenSSH 개발자·GreyNoise·Previdian·watchTower 등 다수 연구기관 확인)

**쉽게 말하면**: 가벼운 리눅스 배포판(Alpine 등)에 쓰이는 'musl'이라는 C 라이브러리와 OpenSSH를 함께 쓰는 서버에서, 비밀번호 로그인을 막아 놓은 계정인데도 아주 긴 비밀번호를 입력하면 뚫리는 결함('SSHole'이라는 이름이 붙음, CVE-2026-123158)이 발견됐습니다. 연구자가 공격 코드를 공개한 지 이틀도 안 돼 실제 공격이 시작됐고, 공격자들은 암호 파일을 훔쳐보거나 자신의 접속키를 몰래 등록해 계속 들어올 수 있게 했습니다. 다행히 지금까지 확인된 실제 성공 사례는 적은 수(한 연구기관 기준 16건)지만, 수정판(10.6p2)이 나온 지 40시간도 안 돼 첫 성공 사례가 나왔다는 점에서 패치를 미루면 위험합니다.
**먼저 할 일(초보용)**: Alpine Linux 등 musl 기반 리눅스 서버를 관리한다면 지금 바로 OpenSSH를 10.6p2 이상으로 업데이트하거나, 업데이트가 어렵다면 SSH 비밀번호 로그인을 끄고 키(key) 인증만 허용하세요.

**개요**: 결함은 계정의 비밀번호 해시 칸이 별표(*, 비밀번호 로그인 차단을 뜻함)로 설정돼 있어도, 아주 긴(비정상적으로 긴) 비밀번호를 넣으면 musl의 해시 함수가 오류로 별표를 반환하는데 OpenSSH가 이를 "일치"로 잘못 처리해 인증을 우회하는 방식이다. 연구자 Ozgun Kultekin이 발견했고, OpenSSH 개발팀은 2026-11-05 10.6p2로 수정판을 냈다. 같은 날 개념증명(PoC) 공격 코드가 공개돼 공격 시도가 시작됐고, watchTower는 11/6 봇넷·암호화폐 채굴과 연결된 공격을 관측했다. GreyNoise는 수정판 출시 약 40시간 뒤인 11/7 00:46(UTC) 첫 성공 악용을 확인했으며, 6개 발신 IP에서 16건의 성공 공격 체인을 기록했다(이는 전체 공격 규모를 대표하지 않는다고 밝혔다). Previdian은 9개국 13개 IP에서 20건의 시도와 성공 사례를, Defused는 소수의 공격자가 시도한 제한적 활동을, watchTower는 봇넷·채굴형 공격을 각각 관측했다. 공격자는 시스템·컨테이너 정찰, 클라우드 메타데이터 서비스 질의, 비밀번호 해시·root SSH 키 읽기 시도, authorized_keys 파일 변조를 했고, 한 공격자는 root 권한을 얻어 파이썬 기반 명령제어(C2) 임플란트 'TAC Agent'를 설치했지만 실제로 명령을 받지는 않았다. GreyNoise는 별도로 22번 포트 스캔 2,750만 건·SSH 접속 시도 2,010만 건을 관측했지만 이를 SSHole 공격으로 확정하지는 않았다.

**왜 일어났나**
- 직접 원인 [확인]: musl의 비밀번호 해시 처리 오류(해시 비교 실패 시 반환값이 "차단"을 뜻하는 별표와 같아짐)와, OpenSSH가 이 반환값을 제대로 구분하지 않은 처리가 겹쳐 비밀번호 인증이 없는 계정도 우회될 수 있었다(OpenSSH 개발팀·연구기관 확인).
- 구조적 원인 [추정 — 분석]: 비밀번호 해시 비교처럼 "에러 상황"과 "정상 차단 상황"의 반환값이 같은 문자(*)로 겹치는 코드 설계는, 한쪽 라이브러리(musl)만 봐서는 드러나지 않고 다른 쪽(OpenSSH)의 처리 방식과 합쳐질 때만 문제가 생긴다 — 이런 "조합형 결함"은 개별 컴포넌트 검증만으로는 찾기 어렵다.

**침투 경로 [확인 — 연구기관 공통]**: 공격자가 비정상적으로 긴 비밀번호로 SSH 로그인 시도(T1190, 노출된 SSH 서비스 악용) → musl 해시 오류로 인증 우회 성공 → 시스템·컨테이너 정찰 및 클라우드 메타데이터 질의(T1613) → 패스워드 해시·root SSH 키 탈취 시도(T1552) → authorized_keys에 공격자 키 추가로 지속 접근 확보(T1098.004) → (일부) C2 임플란트 TAC Agent 다운로드·설치(T1105).

**어떻게 조치하나**
- 즉시: (OpenSSH·연구기관 권고) OpenSSH를 10.6p2 이상으로 업데이트한다. 업데이트가 어려우면 SSH 비밀번호 인증을 비활성화한다. (본 보고서의 권고) `/etc/shadow`에서 비밀번호 필드가 `*`인 계정에 성공한 로그인 기록이 있는지 지금 점검한다.
- 단기: authorized_keys 파일의 비인가 키, TAC Agent 관련 파일·시작 서비스가 있는지 전체 서버를 점검하고, 발견되면 패치 전이라도 로그를 먼저 보존한다.
- 장기: 패스워드 없는 관리자 권한 계정(암호 로그인 차단만으로 안전하다고 여겨진 계정)을 원칙적으로 없애고, 키 기반 인증과 최소 권한 원칙을 함께 적용한다.
- 탐지: 비밀번호 필드가 `*`인 계정의 성공한 로그인, 클라우드 메타데이터 서비스에 대한 비정상 질의를 모니터링한다.

**교훈**: "비밀번호 로그인을 막아 놨다"는 설정이 실제로는 보호 장치가 아니라 공격 표면이 될 수 있다는 점을 보여준다. 수정판이 나온 지 이틀도 안 돼 실제 공격이 성공했다는 사실은, 패치 공개 자체가 공격자들에게 "여기를 보라"는 신호가 되는 시대에 패치 적용 속도가 곧 방어 수준이라는 점을 다시 확인시킨다.

### [D20261110-sonicvpn] SonicWall SSL-VPN SAML 인증(MFA) 우회(CVE-2026-19868) 실제 악용
> 날짜: 연구자 발견·제보 시점 미공개 · 벤더 보안 권고(SNWLID-2026-0014) 공개 2026-11-06 · CISA KEV 등재 2026-11-06 · 유형: VPN 인증 우회(실제 악용 확인) · 행위자: 미귀속 · 지역: 전 세계(해외, 연방기관 포함) · 근거: 확인(벤더 PSIRT 조사·CISA KEV 등재로 실제 악용 확인)

**쉽게 말하면**: 많은 기업이 재택근무·원격 접속에 쓰는 SonicWall 방화벽의 SSL-VPN 기능에서, SAML(회사 로그인을 한 번만 하면 여러 서비스에 쓸 수 있게 해 주는 표준 방식) 인증으로 다중 인증(MFA)을 걸어 놨어도, 다른 로그인 방법의 정상 계정 정보만 있으면 그 MFA를 건너뛸 수 있는 결함(CVE-2026-19868)이 발견됐습니다. SonicWall은 실제 악용 정황을 조사했고, 미국 정부(CISA)도 이 결함이 실제 공격에 쓰이고 있다고 확인해 긴급 수정을 요구했습니다. SonicWall은 지난 7월부터 10월까지도 비슷한 제로데이 공격을 반복해서 당해 온 터라, 이번이 네 번째 연속 사고입니다.
**먼저 할 일(초보용)**: SonicWall SSL-VPN을 SAML 인증(SSO)으로 설정한 조직의 관리자는 지금 바로 SonicOS를 7.3.4-7013(Gen7) 또는 8.2.3-8015(Gen8)로 업그레이드하세요. 이 결함은 우회책이 없어 업그레이드가 유일한 방법입니다.

**개요**: 이 결함(CVSS 7.1)은 SAML로 다중 인증을 적용한 SSL-VPN 서비스에서, 공격자가 다른("대체") 인증 방식의 정상 자격 증명만 가지고 있으면 SAML 통제(여기에 걸린 MFA 포함)를 건너뛸 수 있게 한다. 연구자 Ryan Harris(The Electronic Office)가 발견·제보했고, SonicWall PSIRT는 실제 악용 가능성 제보를 조사한 뒤 즉시 업그레이드를 권고했다. 세부 악용 정황은 공개하지 않았지만, CISA가 이를 실제 악용 확인 카탈로그(KEV)에 등재해 실제 공격이 있었음을 공식 확인했다(연방 민간기관 조치 기한 11/20). 영향받는 버전은 SonicOS Gen7 7.3.3-7015 이하, Gen8 8.2.2-8015 이하이며, 각각 7.3.4-7013·8.2.3-8015에서 수정됐고 우회책은 없다. 같은 보안 권고(SNWLID-2026-0014)에서 관리 인터페이스의 비인증 비인가 작업 결함 2건(CVSS 8.8), SSL-VPN·TACACS+ 서비스의 사전 인증 버퍼 오버플로(서비스 거부), 가상 어플라이언스의 약한 비밀번호 해시까지 총 7건을 함께 수정했다. SonicWall은 2026년 7월(SMA1000 제로데이 2건, 악성코드 배포), 9월(제로데이 2건 연쇄로 RCE), 10월(CVE-2026-102255 최고위험도 결함 악용 시도)에 이어 이번이 네 번째 연속 사고다.

**왜 일어났나**
- 직접 원인 [확인]: SAML 기반 SSL-VPN 인증 로직이 "대체 인증 방식"의 유효 자격 증명을 SAML 통제 우회에 쓸 수 있도록 허용하는 설계·구현 결함이었다(벤더 확인).
- 구조적 원인 [추정 — 분석]: 올해 들어 네 번째로 반복되는 SonicWall 제로데이라는 점에서, 개별 결함 하나를 고치는 패치 대응을 넘어 SSL-VPN·SAML 인증 로직 전반의 설계 재검토가 필요한 신호로 보인다. MFA를 "걸어 놓았으니 안전하다"고 여기기보다, 그 MFA를 구현한 코드 경로 자체도 검증 대상이라는 점을 보여준다.

**침투 경로 [확인 — 벤더·CISA]**: 공격자가 대체 인증 방식의 유효 자격 증명 확보(구체적 입수 경로는 미공개) → SAML 기반 SSL-VPN 로그인 시 MFA 통제 우회(T1556.006) → VPN을 통한 내부망 접근(이후 단계는 공개되지 않음).

**어떻게 조치하나**
- 즉시: (벤더 권고) 7.3.4-7013(Gen7)/8.2.3-8015(Gen8)로 즉시 업그레이드한다(우회책 없음). (본 보고서의 권고) 업그레이드 전이라도 SAML 로그인 접근 로그를 보존한다.
- 단기: 영향 가능 기간 SSL-VPN으로 접속한 계정의 세션을 무효화하고 비밀번호를 재발급하며, 비정상 접근 흔적을 점검한다.
- 장기: SonicWall처럼 반복적으로 제로데이가 발견되는 경계 장비는 원격 접속 경로를 이중화(VPN 업체 다변화 또는 추가 네트워크 분할)하는 것을 검토한다.
- 탐지: 대체 인증 방식으로 로그인한 뒤 곧바로 SAML 전용 리소스에 접근하는 비정상 패턴을 모니터링한다.

**교훈**: 다중 인증(MFA)은 "켜 놨다"는 사실만으로 안전을 보장하지 않는다. MFA를 적용한 로직 자체에 우회 경로가 있다면, 이용자 입장에서는 평소처럼 로그인했을 뿐인데도 보호 장치가 조용히 빠져나가는 셈이다. 같은 벤더에서 반복되는 제로데이는 패치 속도보다 설계 문제를 의심해야 하는 신호다.
