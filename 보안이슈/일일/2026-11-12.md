### [D20261112-gsconst] GS건설 아파트('자이') 커뮤니티 시스템 침해, 입주민 정보·RF카드번호 등 15개 항목 유출 가능성 및 정부 첫 직권조사
> 날짜: 비인가 접근 확인 2026-10-28 22:15경 · 침해 신고 2026-10-29 · 입주민 안내 2026-10-30 · 과기정통부 직권조사 결정·발표 2026-11-11(보도 11-11~12) · 유형: 아파트 커뮤니티 예약·관리 시스템 비인가 접근(경위 직권조사 중) · 행위자: 미귀속 · 지역: 한국 · 근거: 확인(GS건설 신고·공지, 과기정통부 직권조사 발표)

**쉽게 말하면**: GS건설이 운영하는 아파트('자이' 등) 커뮤니티 시설 예약·관리 시스템에 외부 해커가 몰래 접근해, 입주민의 이름·생년월일·휴대전화번호·주소·세대주 여부·암호화된 비밀번호·관리자 ID·출입용 RF카드번호 등 최대 15개 항목이 유출됐을 가능성이 확인됐습니다. GS건설이 침해 신고 후 자체 원인 분석을 이유로 정부(과기정통부·KISA)의 기술지원 조사에 동의하지 않자, 과기정통부는 올해 10월 새로 시행된 개정 정보통신망법에 따라 '침해사고 조사 심의위원회'를 열어 법 시행 후 첫 번째 정부 직권조사를 결정했습니다.
**먼저 할 일(초보용)**: 해당 아파트 커뮤니티 앱·웹사이트를 이용하는 입주민과 관리자는 안전한 기기에서 비밀번호를 즉시 바꾸고(같은 비밀번호를 쓰는 다른 사이트도 함께 변경), 기존 로그인 세션을 모두 로그아웃하세요. 단지 관리사무소나 건설사를 사칭해 출입카드 재발급·관리비 정산을 유도하는 문자·전화에 속지 마세요.

**개요**: 과학기술정보통신부는 2026년 11월 11일 GS건설의 아파트 커뮤니티 시설 예약·관리 시스템(구 FMCS 등) 침해사고의 피해 현황과 사고 원인을 규명하기 위해 직권조사를 실시한다고 발표했다(보안뉴스·데일리시큐 보도). 앞서 GS건설은 10월 28일 오후 10시 15분경 해당 시스템에서 외부 비인가 접근을 확인해 10월 29일 관계기관에 신고하고 10월 30일 입주민에게 유출 가능성을 안내했다. 안내된 유출 가능 항목은 이름, 별명, 생년월일, 휴대전화번호, 성별, 이메일, 주소, 회원번호, 거주 유형, 암호화된 비밀번호, 관리자 ID, 세대주 여부, 회원가입 일시, 최종 로그인 IP 주소, RF카드번호 등 총 15개 항목이다(전체 피해 단지 수와 실제 외부 반출 규모는 최종 확인 중). 특히 RF카드번호는 공동현관 출입이나 커뮤니티 시설 이용과 연계될 수 있는 정보여서 물리적 출입 보안과의 연관성 확인이 필요한 사안이다(유출된 번호만으로 카드 복제·출입이 가능한지는 미확인). GS건설이 신고 당시 자체 원인 분석을 이유로 과기정통부·KISA 기술지원에 미동의하자(GS건설 측은 "조사 미동의가 아니라 자체 원인분석·재발방지 기술지원 미동의이며 조사에 성실히 협조할 것"이라고 해명), 과기정통부는 지난 10월 1일 시행된 개정 정보통신망법상 침해사고 조사 심의위원회를 개최해 **법 시행 이후 첫 직권조사**를 결정했으며, 중대 사고로 판단될 경우 민관합동조사단 구성도 검토할 계획이다.

**왜 일어났나**
- 직접 원인 [확인 — 세부 침투 경로는 직권조사 중]: 아파트 커뮤니티 시설 예약·관리 시스템에 외부 비인가 접근이 발생해 입주민·관리자 관련 15개 항목이 유출 위험에 노출됐다(GS건설 신고·과기정통부 발표). 구체적인 웹/API 취약점이나 계정 탈취 경로는 정부 직권조사 중이어서 단정하지 않는다.
- 구조적 원인 [추정 — 분석]: 아파트 커뮤니티·스마트홈 관리 시스템은 다수 단지의 입주민 실거주 주소·세대주 여부·출입 RF카드번호 등 민감한 주거·물리 보안 정보를 집중 보관하면서도, 핵심 금융·통신망에 비해 보안 관제와 접근 통제가 느슨하기 쉽다(지난 10월 23일 발생한 아파트 생활 플랫폼 '아파트너' 휴대전화번호 반출 사고와도 맞닿아 있는 본 보고서의 분석).

**침투 경로 [매핑 안 함 — 경위 조사 중, 미공개]**: 외부 비인가 접근 사실만 확인됐고 최초 침투 기법은 과기정통부 직권조사 중이어서 ATT&CK 기법을 추측으로 매핑하지 않는다.

**어떻게 조치하나** (본 보고서의 권고이며 정부·기관 지침이 우선)

### [D20261112-xenorchestra] 가상화 관리 도구 Xen Orchestra 인증 우회(VSA-2026-062) 실제 악용 — 빈 JSON 쿠키 하나로 하이퍼바이저 root 장악
> 날짜: Vates 긴급 보안 권고(VSA-2026-062)·패치 공개 2026-11-10 · 보도·분석 2026-11-11~12 · 유형: 가상화 관리 콘솔 인증 우회 및 하이퍼바이저 장악(실제 악용 확인) · 행위자: 미귀속 · 지역: 전 세계(해외) · 근거: 확인(Vates 공식 보안 권고·보안 연구진 관측)

**쉽게 말하면**: 기업들이 여러 대의 가상 서버(가상머신)를 한꺼번에 관리할 때 쓰는 웹 도구 '젠 오케스트라(Xen Orchestra)'에서, 아이디나 비밀번호를 전혀 몰라도 로그인 과정을 통째로 건너뛸 수 있는 치명적인 결함(VSA-2026-062)이 실제 해킹 공격에 악용됐습니다. 공격자가 쿠키 값에 '빈 괄호(`j:{}`)' 하나만 넣어서 보내면, 프로그램이 이를 제대로 검사하지 않고 데이터베이스 맨 첫 줄에 있는 토큰(보통 최고 관리자 계정)을 그대로 꺼내 줘서 곧바로 관리자 권한을 얻게 됩니다. 이를 통해 공격자는 관리 도구뿐 아니라 그 아래 연결된 물리 가상화 서버(XCP-ng 하이퍼바이저) 전체의 최고 권한(root)까지 장악했습니다.
**먼저 할 일(초보용)**: Xen Orchestra 또는 Xen Orchestra Appliance(XOA)를 운영하는 관리자는 **지금 즉시 관리 웹 화면이 외부 인터넷에서 접속되지 않도록 방화벽으로 차단**하고, 네트워크 패킷·호스트 로그를 보존한 뒤 수정 버전(안정 채널 6.9.2, 최신 채널 6.10.1 이상 — 당시 기준)으로 업데이트하세요. 이 공격은 일반 관리 로그에 흔적이 안 남으므로, 인터넷에 한 번이라도 열려 있었다면 관리자 토큰·연동 비밀번호를 전부 바꾸고 서버에 낯선 가상머신(`pivot2`)이나 예약 작업(`/etc/cron.d/zz-ustar`)이 없는지 반드시 확인하세요.

**개요**: 가상화 솔루션 기업 Vates는 2026-11-10 치명적(Critical) 등급 보안 권고 **VSA-2026-062**(공개 시점 CVE 번호 미부여)를 발표하고, 자사의 가상화 통합 관리 플랫폼 Xen Orchestra(XO) 및 Xen Orchestra Appliance(XOA)의 인증 우회 취약점이 실제 공격에서 악용(in the wild)되고 있음을 확인했다. 결함은 REST API의 쿠키 파싱 과정에서 발생한다. 공격자가 `authenticationToken=j:%7B%7D`(디코딩 시 `j:{}`) 형태의 조작된 쿠키를 보내면 쿠키 파서가 이를 문자열이 아닌 빈 JSON 객체(`{}`)로 변환해 토큰 검증기에 넘긴다. 토큰 검증기가 입력값이 문자열인지 확인하지 않고 빈 객체를 그대로 데이터베이스 조회 조건(필터 없는 전체 조회)으로 처리하면서, 저장소에서 가장 먼저 발견되는 만료되지 않은 토큰(대부분 최초 생성된 최고 관리자 토큰)의 소유자로 공격자를 로그인시켜 준다. 이후 공격자는 인증된 `/rest/v0/users/me/authentication_tokens` 경로에서 재사용 가능한 로그인 토큰을 추출하고, 관리 대상 가상화 풀(Pool)에서 임의 코드를 실행해 연결된 XCP-ng 하이퍼바이저 노드의 root 권한까지 장악했다. 보안 연구진과 Vates가 확인한 실제 공격에서는 특정 악성 IP(`91.211.251[.]112`) 및 Tor 히든 서비스(`.onion`)가 사용됐으며, 호스트 내 악성 예약 작업(`/etc/cron.d/zz-ustar`) 등록과 `pivot2`라는 이름의 은닉 가상머신 생성 등 지속성 확보 행위가 관측됐다. 특히 비인증 공격이 성공하더라도 XO의 표준 애플리케이션 로그에는 인증 우회 기록이 남지 않는다.

- 탐지: HTTP 쿠키 헤더 내 `j:%7B`·`j:{` 패턴, `/rest/v0/users/me/authentication_tokens`에 대한 비정상 호출, 하이퍼바이저 호스트의 `/etc/cron.d/` 파일 생성 및 비인가 VM 생성 이벤트를 탐지한다.

**교훈**: 가상화 관리 도구가 뚫리는 것은 서버 한 대가 뚫리는 것이 아니라 **데이터센터 전체의 바닥(하이퍼바이저)이 통째로 넘어가는 것**이다. 더욱이 공격이 성공해도 애플리케이션 로그에 남지 않는다는 점은, 왜 관리 화면을 인터넷에서 완전히 숨기는 것이 패치보다 먼저여야 하는지를 명확히 보여준다.

**먼저 할 일(초보용)**: SAP NetWeaver AS ABAP 및 SAP Web Dispatcher를 운영하는 기업은 SAP가 배포한 2026년 11월 보안 패치(Note #3778530, #3778556, #3798345, #3849308)를 최우선으로 적용하세요. 이때 내부 커널만 고치고 바깥쪽 **웹 디스패처(Web Dispatcher) 업데이트를 하나라도 빠뜨리면 구멍이 그대로 남으므로** 모든 웹 디스패처를 빠짐없이 함께 업데이트하고, 만약 침해가 의심된다면 패치만으로는 이미 발급된 세션·토큰이 사라지지 않으므로 안전한 환경에서 기존 세션을 무효화하세요.

**개요**: SAP는 2026년 11월 정기 보안 패치(Security Patch Day)를 통해 총 17건의 보안 노트를 발표했으며, 이 가운데 **CVSS 10.0(만점) 취약점이 이례적으로 4건** 포함됐다(Onapsis Research Labs 발굴·분석 및 RedRays·The Hacker News·보안뉴스 보도). 4건 모두 사전 인증이나 사용자 상호작용이 필요 없다.
1. **ICM2Shell — CVE-2026-76964(SAP Note #3778530, NetWeaver AS ABAP의 Internet Communication Manager) 및 CVE-2026-89126(SAP Note #3778556, SAP Web Dispatcher / HANA XS Advanced 내장 포함)**: 두 컴포넌트가 공유하는 SAP 커널 코드에서 분할(fragmented)된 웹소켓(WebSocket) 제어 메시지를 재조합할 때 길이 값 검증이 누락돼, 로그인 전 단계에서 힙 메모리 범위 밖 쓰기(out-of-bounds write)가 발생한다. SAP 환경에서 웹소켓은 기본 활성화돼 있고 일부 기본 서비스는 인증 없이 웹소켓 연결을 수락하므로, 비인증 원격 공격자가 조작된 트래픽을 보내 시스템 설치 소유자(`<sid>adm`) 권한으로 임의 OS 명령을 실행하거나 서비스를 중단시킬 수 있다.
2. **ProxyGate — CVE-2026-89103(SAP Note #3798345, SAP Gateway)**: SAP 게이트웨이가 높은 권한을 부여하는 기본 접근 제어 목록(ACL)을 활성화해, 네트워크 접근이 가능한 비인증 외부 공격자가 내부 애플리케이션 서버로 위장해 비인가 작업을 수행하고 시스템을 완전 장악할 수 있는 접근 통제 결함이다.
3. **SAML 2.0 인증 우회 — CVE-2026-120017(SAP Note #3849308, SAP NetWeaver AS ABAP 및 ABAP Platform)**: 특정 설정에서 수신되는 SAML 2.0 인증 증명(assertion)의 검증이 불충분해, 비인증 공격자가 조작된 데이터를 제출함으로써 인증을 우회하고 관리자 등 특권 계정을 사칭해 시스템과 연결된 후속 시스템까지 장악할 수 있는 결함이다(지난 6월 수정된 CVE-2026-44748과 달리 일반 계정조차 필요 없다).

**왜 일어났나**
- 직접 원인 [확인: SAP, Onapsis, MITRE]: (1) ICM·Web Dispatcher 커널의 분할 웹소켓 프레임 재조합 시 길이 검증 누락으로 인한 메모리 오염(CVE-2026-76964·89126) (2) SAP Gateway 기본 ACL의 과도한 권한 부여로 외부 호스트를 내부 앱 서버로 오인(CVE-2026-89103) (3) SAML 2.0 인증 응답 검증 미흡(CVE-2026-120017).
- 구조적 원인 [추정 — 분석]: 외부 웹 트래픽을 최전선에서 받아 내부 ERP로 전달하는 Web Dispatcher와 ICM이 동일한 C/C++ 기반 커널 파서를 공유하고 기본 설정으로 비인증 웹소켓 엔드포인트를 열어 두어, 파서 결함 하나가 곧바로 경계 장비와 코어 서버 양쪽의 비인증 원격 코드 실행으로 이어지는 구조(본 보고서의 분석).

**침투 경로 [후보 — 공개 시점 실제 악용 미확인, 취약점 메커니즘 기준]**: 외부 노출된 SAP Web Dispatcher·ICM·Gateway·SAML 엔드포인트에 조작된 웹소켓 트래픽·게이트웨이 요청·SAML 데이터를 전송해 비인증 침투(T1190, 후보) → (ICM2Shell의 경우) 힙 메모리 오염을 통해 `<sid>adm` 권한으로 운영체제 명령 실행(T1059, 후보). 실제 공격 악용 사례는 공개 시점에 보고되지 않아 모두 `후보`로 매핑한다.

**어떻게 조치하나** (벤더·연구기관 권고 및 본 보고서 권고)
- 즉시: SAP 커널 및 **모든 SAP Web Dispatcher 인스턴스(HANA XS Advanced 내장 포함)**에 2026년 11월 패치(Note #3778530, #3778556, #3798345, #3849308 등)를 즉시 적용한다. 패치 전 웹 디스패처·ICM·게이트웨이·SAML 감사 로그를 보존한다.
- 단기: SAML 결함(CVE-2026-120017)과 게이트웨이 결함(CVE-2026-89103)은 별도의 설정 우회책(workaround)이 없으므로 패치가 유일한 해결책이다. 패치 후 게이트웨이 접근 규칙(ACL) 강화 설정을 활성화하고 게이트웨이 포트(`33xx`)가 인터넷이나 일반 사용자 망에 노출되지 않도록 방화벽으로 차단하며, 사용자가 ICM에 직접 붙지 않고 반드시 패치된 Web Dispatcher만 거치도록 구성한다. - 장기: 인터넷 경계에 놓인 SAP Web Dispatcher의 불필요한 기본 웹소켓 서비스 노출을 최소화하고, ERP 코어 커널 패치 주기를 일반 업무 변경 관리보다 우선하는 긴급 보안 트랙으로 분리한다.
- 탐지: Web Dispatcher 및 ICM으로 유입되는 비정상 분할 WebSocket 제어 프레임·크래시 로그, 외부 IP의 게이트웨이 포트(`33xx`) 접속 시도, 예상치 못한 출처의 특권 계정 SAML 로그인 이벤트를 모니터링한다.

**교훈**: 지난주 바라쿠다 보안장비 결함(`D20261111-barracuda`)이 패치 공개 7일 만에 실제 악용으로 전환됐듯, CVSS 10.0 만점 결함 4건이 한꺼번에 공개된 SAP 환경도 공격자들의 최우선 역분석 표적이 된다. 특히 바깥쪽 Web Dispatcher 하나만 패치를 빼먹어도 그 지점이 그대로 돌파구가 된다.

### [D20261112-screenconnect-msp] ConnectWise ScreenConnect MSP 표적 캠페인 — 서드파티 확장(RMM+ 계열) 악용으로 클라우드 파트너 400여 곳 긴급 차단
> 날짜: ConnectWise·Huntress 경고 및 확장 강제 비활성화 2026-11-10~11 · 유형: 원격 관리 도구(ScreenConnect) 패널 및 서드파티 확장 악용 공급망·연쇄 침해 · 행위자: 미귀속 · 지역: 전 세계(해외) · 근거: 확인(ConnectWise 공식 공지·Huntress SOC 분석)

**쉽게 말하면**: 여러 고객사의 PC와 서버를 원격으로 관리해 주는 IT 관리업체(MSP)들이 쓰는 원격 제어 도구 '커넥트와이즈 스크린커넥트(ConnectWise ScreenConnect)' 환경을 노린 실제 해킹 캠페인이 포착됐습니다. 공격자는 스크린커넥트 자체의 결함이 아니라, 탈취한 계정·세션으로 관리 화면에 들어간 뒤 원격 명령 실행 기능을 가진 제3자 부가기능(RMM+ 계열 확장 프로그램 5종)을 악용해 하위 고객사 컴퓨터 수백 대에 공격자가 조종하는 '가짜 스크린커넥트 프로그램'을 몰래 추가로 깔았습니다. 더 위험한 것은, 관리업체 직원이 감염된 고객 컴퓨터를 고치려고 원격 접속하는 순간 거꾸로 직원 컴퓨터의 로그인 토큰이 털려 다른 고객사 관리 화면까지 연쇄 감염될 수 있다는 점입니다.
**먼저 할 일(초보용)**: ScreenConnect를 운영하는 MSP 및 기업 관리자는 서드파티 확장 프로그램 5종(**RMM+, RMM Plus, RMM Plus Password Link, RMM+ Password Link, Labtech Plus**)이 설치돼 있다면 즉시 비활성화·제거하세요(클라우드 버전은 ConnectWise가 약 400곳에서 강제 차단함). 또한 고객사 엔드포인트에 우리 회사가 아닌 낯선 서버 주소로 연결되는 ScreenConnect 클라이언트가 추가로 깔려 있지 않은지 전수 점검하세요.

**개요**: 보안 기업 Huntress와 ConnectWise는 2026-11-10~11 관리형 서비스 제공사(MSP)의 ConnectWise ScreenConnect 환경을 겨냥한 활발한 악성코드 캠페인을 확인하고 긴급 경고를 발령했다. 두 회사의 발표(BleepingComputer·The Hacker News 보도)에 따르면, ScreenConnect 코어 소프트웨어 자체의 신규 취약점이나 ConnectWise 본사 인프라 침해 증거는 없으나, 공격자들이(탈취된 자격 증명이나 가로챈 운영자 세션 등을 통해) MSP의 ScreenConnect 관리 패널에 접근한 뒤 원격 명령 실행 API를 노출하는 서드파티 확장 기능 5종(**RMM+, RMM Plus, RMM Plus Password Link, RMM+ Password Link, Labtech Plus**)과 패널의 'Run Command' 기능을 악용했다. 이를 통해 다수의 침해된 MSP에 연결된 하위 고객사 엔드포인트 수백 대에 공격자의 서버로 연결되는 변조(rogue) ScreenConnect 클라이언트를 지속성 백도어로 배포했다. 특히 Huntress는 MSP 엔지니어가 이미 감염된 고객 엔드포인트를 조사·복구하기 위해 대화형(interactive) 세션으로 접속할 경우, 엔드포인트의 악성코드가 역방향으로 엔지니어 워크스테이션을 타고 넘어와 인증 토큰이나 브라우저 세션을 긁어낸 뒤 엔지니어가 접근할 수 있는 다른 ScreenConnect 패널로까지 확산(reverse pivot)하는 위험을 확인했다. ConnectWise는 예방 조치로 자사 클라우드 파트너 환경 약 400곳에서 해당 확장 5종을 강제 비활성화했으며, 자체 서버(On-premises) 운영 고객에게도 즉시 수동 비활성화할 것을 촉구했다.

Moller-Maersk는 2026-11-10~11(현지시간) 과거 기업 인수를 통해 물려받은 로컬 레거시 시스템(보안 업계 및 보도에서는 2022년 머스크가 36억 달러에 인수한 계약 물류 기업 LF Logistics의 OCF/LF 플랫폼으로 지목)에 외부 비인가 접근과 데이터 추출이 발생했다고 공식 확인했다(BleepingComputer·SecurityAffairs·Container News 보도). 동시에 'WhiteArmor'라고 자칭하는 랜섬웨어·협박 그룹이 다크웹 유출 사이트에 머스크를 등재하고, 수만 건의 운전기사 프로필·최고관리자(`SUPER_ADMIN`) 계정·모바일 기기 로그·창고 재고 데이터·배송 영수증 등 약 100GB의 데이터를 탈취했다며 30일 이내에 비트코인 500만 달러를 지불하라고 요구했다([주장]). 이에 대해 머스크는 해당 침해가 과거 인수에서 비롯된 격리된 로컬 레거시 시스템에 국한됐으며, 초기 조사 결과 민감한 데이터가 노출되지 않았고 API·EDI로 연결된 머스크의 광역 인프라나 고객 대면 화물 예약·운송 시스템에는 영향이 없어 정상 운영 중이라고 밝혔다([확인]).

**왜 일어났나**
- 직접 원인 [확인 — 세부 침투 경로는 미공개]: 과거 인수 법인에서 물려받은 로컬 레거시 시스템에 외부 비인가 접근이 발생해 데이터가 추출됐다(머스크 공식 확인). 어떤 취약점이나 계정으로 침투했는지는 공개되지 않았다.
- 구조적 원인 [추정 — 분석]: 글로벌 대기업이 타 기업(물류·창고 업체 등)을 인수·합병한 뒤, 기존에 쓰던 지역 단위 레거시 시스템을 완전히 퇴역시키거나 본사 수준의 보안 관제·패치 체계로 통합하기까지의 과도기가 공격자들의 단골 침투 지점이 된다. 다만 해당 레거시 시스템이 머스크 본사 코어망과 네트워크적으로 분리돼 있었던 덕분에 전사 물류 마비로 번지지 않았다(본 보고서의 분석).

**침투 경로 [확인(갈취 요구) / 최초 침투는 미공개]**: 인수 법인의 로컬 레거시 시스템에 비인가 접근해 데이터 추출(초기 침투 수단은 미공개여서 매핑 안 함) → 추출한 데이터를 빌미로 다크웹 유출 사이트에 등재하고 500만 달러 몸값 요구(T1657, 확인 — 단 100GB 규모와 세부 항목은 공격자 주장).

**어떻게 조치하나** (본 보고서의 권고)
- 즉시: 침해된 로컬 레거시 시스템을 외부 네트워크 및 본사 연동 구간에서 완전히 격리하고, 포렌식 증거(접근 로그·DB 추출 기록·디스크 이미지)를 신속히 보존한다. 침해된 서버에서 새 비밀번호나 키를 발급하지 않는다.
- 단기: 공격자가 최고관리자(`SUPER_ADMIN`) 계정 등을 확보했다고 주장하고 있으므로, 해당 레거시 시스템의 모든 관리자·사용자 계정과 세션·토큰·API 연동 키를 안전한 환경에서 전면 폐기·교체하고, 본사나 타 자회사 시스템에 동일한 비밀번호·키가 재사용됐는지 전수 점검한다. 레거시 시스템의 기능은 검증된 신규 플랫폼으로 이전하고 기존 서버는 재구축 또는 영구 폐기한다.
- 장기: 기업 인수·합병(M&A) 시 인수 대상 기업의 외부 노출 자산·레거시 서버 전수 목록화와 본사 코어망 연결 전 강제 격리·보안 실사(Due Diligence)를 표준 절차로 운영한다.
- 탐지: 인수 법인·자회사 레거시 서버에서의 대용량 데이터 외부 전송 및 본사 API·EDI 게이트웨이로의 비정상 접근 시도를 모니터링한다.

**교훈**: 이번 사건은 기업 인수 후 남은 '옛날 시스템(레거시)'이 어떻게 공격 표적이 되는지 보여 주는 동시에, **네트워크 격리(Segmentation)**가 왜 중요한지도 함께 보여 준다. 옛 시스템 하나가 뚫렸더라도 본사 핵심 물류망과 철저히 분리돼 있었기 때문에 2017년 NotPetya 사태 때와 같은 전 세계 물류 마비를 막을 수 있었다.

## 6. 검증 수준과 한계

- CISA KEV 카탈로그를 2026-11-12 직접 조회한 결과 11-10 등재분(어제 보고서에 수록한 6건) 이후 신규 등재 항목은 없었다.
- SAP(`CVE-2026-76964`, `CVE-2026-89126`, `CVE-2026-89103`, `CVE-2026-120017`), Ivanti(`CVE-2026-121653`, `CVE-2026-121683`), Fortinet(`CVE-2026-126170`, `CVE-2026-126253`) 취약점은 MITRE CVE 공식 API 레코드와 벤더·연구기관 발표를 직접 대조해 확인했으며, 공개 시점 실제 악용이 확인되지 않아 ATT&CK 매핑에서 `후보`로 구분했다. 수정 버전 번호는 발표 당시 기준이므로 실제 조치 시 각 벤더의 최신 보안 권고를 재확인해야 한다.
- Xen Orchestra(`VSA-2026-062`)는 공개 시점 CVE 번호가 부여되지 않았으나 벤더(Vates) 공식 권고로 실제 악용과 기술 세부가 확인됐다.
- GS건설(`D20261112-gsconst`)은 최초 침투 경로가 정부 직권조사 중이어서 매핑하지 않았고, 섹타나인(`D20261112-secta9ine`)은 가맹점 관리자 계정 침해와 고객 정보 유출만 확인되고 계정 탈취 수단은 미공개여서 확인된 범위만 매핑했다. 머스크(`D20261112-maersk`) 사건에서 100GB 규모와 세부 항목은 공격자(WhiteArmor)의 일방 주장(`[주장]`)으로 회사의 공식 확인 범위와 엄격히 구분했다.
- **ATT&CK 버전 확인 결과**: https://attack.mitre.org/tactics/enterprise/ 에서 현재 공식 버전이 **v20.1**임을 확인했다(작업 지침은 v19.2 기준, 본 저장소 카탈로그는 v20.0 기준). 전술 15개 체계는 동일하므로 임의 대규모 재매핑 없이 기존 카탈로그 범위에서 매핑했다.
- **독립 교차 검토**: 현재 실행 환경이 Gemini(Antigravity)여서 지침 8번에 따라 Gemini 자체 교차 검토를 수행해 사실관계·근거 표기·ATT&CK 전술-기법 일치·초보용 문장 정확성을 점검했다.
