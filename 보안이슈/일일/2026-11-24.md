**먼저 할 일(초보용)**: 윈도우 서버(IIS)에서 `.aspx`로 끝나는 **ASP.NET WebForms 웹사이트나 사내 업무 포털**을 운영하는 기업·공공기관·대학의 시스템 관리자는 지금 즉시 모든 웹 서버의 **`bin/` 폴더 안에 `Idunno.AntiCsrf.dll` 파일이 있는지, 그리고 `Web.config` 설정 파일의 `<httpModules>` 또는 `<modules>` 항목에 `Idunno.AntiCsrf` / `AntiCsrfModule`이 적혀 있는지 전수 검색**하세요. 만약 발견된다면 공식 패치가 존재하지 않으므로 **즉시 `Web.config`에서 해당 모듈 등록을 지우고 `Idunno.AntiCsrf.dll` 파일을 삭제**한 뒤 마이크로소프트가 공식 지원하는 내장 방어 기능(`System.Web.Helpers.AntiForgery` 또는 MAC 검증이 켜진 `ViewStateUserKey`)으로 교체해야 하며, 이미 공격을 받았을 가능성에 대비해 `Web.config`에 적힌 데이터베이스 비밀번호와 암호화 키(`machineKey`)를 안전한 환경에서 즉시 새로 발급하세요.

**개요**: 구글 클라우드 **맨디언트(Mandiant)**는 공식 취약점 공시(**`MNDT-2026-0048`**)와 MITRE CVE 공식 레코드(**`CVE-2026-131914`**, Mandiant CNA 발행)를 통해, 과거 마이크로소프트의 오픈소스 호스팅 사이트였던 CodePlex에서 배포돼 수많은 레거시 ASP.NET WebForms 애플리케이션에 탑재된 서드파티 CSRF 방어 라이브러리 **`Idunno.AntiCsrf`(`0.9.1.0` 및 `0.9.1 Beta` 이하 전 버전)**에 치명적인 비인증 역직렬화 원격 코드 실행(RCE) 취약점이 존재한다고 발표했다(MITRE CVE API 11/24 직접 조회 확인, The Hacker News 등 확인).
- **취약점 작동 구조 — 왜 '보안 모듈'이 로그인 전(Pre-Auth) 원격 코드 실행 통로가 됐는가 [확인: MITRE CVE `CVE-2026-131914`, Mandiant `MNDT-2026-0048`]**:
  1. **이중 제출 쿠키(Double-submit cookie) 검증 과정의 치명적 설계 오류(CWE-502 / CAPEC-586)**: `Idunno.AntiCsrf`의 HTTP 모듈(`AntiCsrfModule`)은 ASP.NET WebForms 엔드포인트(`.aspx`)로 들어오는 HTTP POST 요청을 IIS 파이프라인의 초기 단계(`PreRequestHandlerExecute`, 즉 실제 페이지의 `Page_Load`가 실행되기 전)에서 가로채 CSRF 토큰 쿠키와 폼 필드(`__CSRFTOKEN`)가 일치하는지 검사한다.
  2. 그런데 이 모듈은 사용자가 보낸 `__CSRFTOKEN` 폼 필드의 값을 검증할 때, **아무런 암호화 서명(MAC)이나 무결성 검증도 하지 않은 상태(unkeyed)에서 닷넷의 위험한 직렬화기인 `System.Web.UI.ObjectStateFormatter`를 사용해 먼저 역직렬화(Deserialization)부터 수행**해 버린다.
  3. **단 한 번의 비인증 POST 요청으로 IIS(`w3wp.exe`) 장악**: 결과적으로 로그인하지 않은 원격 공격자는 인터넷에 열려 있는 아무 `.aspx` 페이지에나 비어 있지 않은 임의의 쿠키 값과 함께, `__CSRFTOKEN` 폼 필드에 Base64로 인코딩된 `.NET ObjectStateFormatter` 가젯 체인(예: `ysoserial.net` 페이로드)을 담아 HTTP POST 요청 한 번만 보내면 즉시 IIS 워커 프로세스(`w3wp.exe`) 권한으로 원격 임의 코드를 실행할 수 있다(심지어 해당 `.aspx` 페이지에 `<form runat="server">`가 없거나 익명 접근 페이지여도 모듈이 등록돼 있으면 파이프라인 앞단에서 무조건 실행된다).
- **왜 패치가 없고 위험도가 극도로 높은가(`exploitMaturity: ATTACKED`)**:
  - MITRE CVE 공식 레코드의 CVSS v4.0 벡터(`CVSS:4.0/AV:N/AC:L/AT:N/PR:N/UI:N/VC:H/VI:H/VA:H/SC:N/SI:N/SA:N/E:A`, 기본 점수 **9.3 Critical**)에는 공격 성숙도가 **`exploitMaturity: ATTACKED`**로 기록돼 있으며, `.NET ObjectStateFormatter`는 이미 공개된 표준 가젯 체인 도구(`ysoserial.net`)로 즉시 무기화가 가능하다.
  - 무엇보다 `Idunno.AntiCsrf` 프로젝트는 호스팅되던 CodePlex가 폐쇄되면서 수년 전 개발이 완전히 중단(Abandoned)돼 **공식 벤더 패치가 영원히 제공되지 않는다**.

**왜 일어났나**
- 직접 원인 [확인: Mandiant, MITRE CVE]: `Idunno.AntiCsrf`(`0.9.1 Beta` 이하)가 이중 제출 쿠키와 폼 필드를 비교할 때 외부 입력값(`__CSRFTOKEN`)에 대해 암호학적 MAC 검증 없이 `ObjectStateFormatter.Deserialize()`를 호출하여 신뢰할 수 없는 데이터의 역직렬화(객체 주입)를 허용했다.
- 구조적 원인 [추정 — 분석]: (1) **'10년 전 외주 개발사가 넣어 둔 좀비 오픈소스 DLL 하나가 서버 전체를 무너뜨리는 레거시 기술 부채'**: 한국과 전 세계의 수많은 공공기관, 대학교 학사/산학단 시스템, 금융사 부속 웹 포털, 제조사 ERP는 2010년대에 개발된 ASP.NET WebForms(`.aspx`)를 아직도 그대로 운영하고 있다. 당시 개발자들이 CSRF 보안성 심사를 통과하려고 CodePlex에서 내려받아 `bin/` 폴더에 복사해 넣은 `Idunno.AntiCsrf.dll` 파일 하나는, 이후 10년 동안 누구도 소스코드나 버전을 들여다보지 않는 '투명 인간' 상태로 서버에 박혀 있다가 오늘날 비인증 RCE 시한폭탄이 됐다 (2) 특히 `NuGet` 패키지 매니저가 정착되기 전에 수동으로 `bin/` 폴더에 복사해 넣은 `.dll` 파일들은 일반적인 SBOM(소프트웨어 자재 명세서)이나 패키지 의존성 스캐너에도 잡히지 않는 경우가 많아 파일시스템 전수 검색이 필수적이다(본 보고서의 분석).

**침투 경로 [확인 / 후보 — Mandiant `MNDT-2026-0048` 및 MITRE CVE `CVE-2026-131914` 기준]**: 비인증 원격 공격자가 인터넷에 노출된 ASP.NET WebForms(`.aspx`) 웹 서버에 임의의 쿠키와 조작된 `.NET ObjectStateFormatter` 역직렬화 페이로드(`__CSRFTOKEN` 폼 필드)가 담긴 HTTP POST 요청을 전송해 초기 침투(T1190, 확인: CVSS v4.0 `exploitMaturity: ATTACKED` 및 Mandiant 권고 확인) → IIS 파이프라인 초기 단계(`PreRequestHandlerExecute`)에서 서명 검증 없는 역직렬화가 트리거되어 IIS 작업 프로세스(`w3wp.exe`) 컨텍스트에서 원격 임의 코드 실행(T1059, 확인).

**어떻게 조치하나** (Mandiant 권고 및 본 보고서 권고)
- 즉시: (모든 윈도우 IIS / ASP.NET WebForms 운영 조직) (1) IIS 웹 로그(W3SVC)와 애플리케이션 이벤트 로그를 신속히 보존한다. (2) **공식 패치가 존재하지 않으므로 유일한 근본 조치는 '즉시 제거(Removal)'다.** 사내외 모든 윈도우 웹 서버에서 아래 두 가지를 즉시 전수 스캔하여 제거한다:
  - ① 웹 애플리케이션 디렉터리(특히 `bin/` 폴더 및 하위 폴더)에서 **`Idunno.AntiCsrf.dll`** 파일(또는 내부에 `Idunno.AntiCsrf` / `AntiCsrfModule` 네임스페이스를 포함한 재컴파일된 커스텀 DLL)을 찾아 즉시 삭제한다.
  - ② 모든 **`Web.config`**(및 상위 `applicationHost.config`) 파일에서 `<httpModules>`, `<modules>`, `<configSections>` 내 **`Idunno.AntiCsrf`** 또는 **`AntiCsrfModule`** 참조 구문을 제거한다.
- 단기: **보안 모듈을 제거한 자리에 공식 지원 CSRF 방어를 적용하고, 이미 역직렬화 공격을 받았는지 포렌식 감사를 수행해야 한다.**
  1. **마이크로소프트 공식 지원 CSRF 방어로 대체**: 삭제한 모듈 대신 마이크로소프트가 공식 지원하는 내장 `System.Web.Helpers.AntiForgery`(`@Html.AntiForgeryToken()` / `AntiForgery.Validate()`), 또는 암호화 및 MAC 검증(`EnableViewStateMac=true`)이 강제된 WebForms 고유 기능인 **`Page.ViewStateUserKey`**로 즉시 전환한다.
  2. **침해 흔적 헌팅 및 `machineKey`·DB 암호 전면 교체**: IIS 로그에서 평소 POST 요청을 받지 않는 `.aspx` 엔드포인트에 대해 비정상적으로 큰 요청 크기(`cs-bytes` 증가)를 가진 POST 요청이 들어와 `500` 또는 `302` 응답을 반환한 기록이나, `w3wp.exe`가 `cmd.exe`·`powershell.exe`를 실행한 흔적, 웹 루트 내 웹셸(`.aspx`, `.ashx`, `.asmx`) 생성 여부를 조사한다. 단 한 번이라도 의심 요청이 확인되면 **`Web.config` 및 서버에 저장된 `.NET machineKey`(이게 털리면 모듈을 지워도 ViewState 역직렬화로 다시 RCE가 가능하다), DB 연결 문자열 비밀번호, 서비스 계정 자격 증명을 안전한 환경에서 전면 교체**하고 서버를 재구축해야 한다.
- 장기: `NuGet`이나 `package.json`에 적힌 선언적 의존성뿐 아니라 레거시 웹 서버의 `bin/`, `lib/` 폴더에 수동 복사된 **바이너리(`.dll`, `.jar`)의 파일 해시와 PE/메타데이터까지 전수 수집하는 바이너리 기반 SBOM 체계**를 구축해, 유지보수가 중단된(Abandoned/EOL) 오픈소스 컴포넌트를 퇴출한다.
- 탐지: WAF에서 `.aspx` 경로로 유입되는 HTTP POST 요청 본문 중 `__CSRFTOKEN` 파라미터에 Base64로 인코딩된 `.NET ObjectStateFormatter` 매직 바이트(`/wEP` 등)나 긴 직렬화 페이로드가 포함된 요청을 즉시 차단·경보하고, EDR에서 `w3wp.exe`의 비정상 자식 프로세스 생성을 차단한다.

**교훈**: `CVE-2026-131914`(`Idunno.AntiCsrf`)는 두 가지 역설을 보여준다. 첫째, **"해킹(CSRF)을 막으려고 깐 보안 라이브러리가 오히려 가장 치명적인 비인증 원격 코드 실행(RCE) 구멍을 열어 주었다"**는 것이고, 둘째, **"오픈소스 개발자가 10년 전에 프로젝트를 접었기 때문에 기다려도 패치가 영원히 나오지 않는다"**는 것이다. 특히 국내 대학·공공기관·중견기업의 오래된 `.aspx` 웹사이트들은 외주 개발 당시 들어간 `bin/` 폴더 속 `.dll` 목록을 관리자가 모르는 경우가 많으므로, 오늘 즉시 윈도우 웹 서버 전체에서 `Idunno.AntiCsrf.dll` 파일 검색 명령을 돌려야 한다.

- 단기: **이름만 바꾼 오픈소스 VPN 브리지(`SoftEther` 등)를 잡아내려면 파일명이 아니라 '행위와 내부 아티팩트'를 봐야 한다.**
  1. **네트워크 어댑터·브리지 생성 및 비인가 VPN 터널 차단**: `SoftEther VPN Bridge`는 이름을 `netcapa.exe`로 바꾸더라도 작동하려면 윈도우 네트워크 스택에서 가상 네트워크 어댑터·로컬 브리지(Local Bridge / 패킷 드라이버)를 바인딩하고 외부 서버로 지속적인 암호화 터널 연결을 맺어야 한다. EDR에서 미승인 실행 파일이 네트워크 어댑터 바인딩이나 Raw 소켓/패킷 캡처 드라이버를 로드하는 행위를 차단하고, 사내 서버가 `api.telegram.org`, `discord.com`, 또는 미승인 외부 IP로 장시간 VPN/TLS 터널을 유지하는 것을 방화벽에서 차단해야 한다.
  2. **외주 위탁 웹사이트 내 내부 인사·외교관 디렉터리 전면 제거**: 외교부·정부 부처가 행사·홍보·민원용으로 외부 외주업체에 맡긴 웹사이트 DB에는 공무원이나 해외 주재관의 내부 연락처 레코드를 절대 동기화하거나 보관하지 않도록 물리적으로 분리한다.
- 장기: 서버 운영 환경에서는 파일 이름이나 자체 서명이 아닌 **신뢰할 수 있는 코드 서명 인증서와 경로 기반의 애플리케이션 허용 목록(Application Allowlisting — AppLocker / WDAC)**을 적용해, 공격자가 변조 컴파일한 `netcapa.exe` 같은 미서명(또는 가짜 서명) 바이너리가 아예 실행되지 못하도록 막는다.
- 탐지: YARA 및 EDR 규칙에 파일명 대신 `SoftEther` 고유 내부 문자열, `vpnbridge.pdb` 디버그 경로, `SoftEther Project` 레지스트리 키 생성 이벤트를 등록해 리브랜딩된 변종까지 실시간 탐지한다.

**교훈**: `Webworm`의 `netcapa.exe` 사례는 **"공격자는 오픈소스(`SoftEther VPN`)의 껍데기만 '네트워크 감시 도구(`NtMonitor`)'로 갈아입혀 쓰는데, 방어자는 아직도 알려진 악성코드 파일 이름과 해시값만 찾고 있다"**는 현실을 꼬집는다. 아무리 프로그램 이름과 회사 이름을 가짜로 꾸며도 **컴파일할 때 남은 `vpnbridge.pdb` 한 줄과 레지스트리의 `SoftEther Project` 흔적, 그리고 외부로 나가는 VPN 터널 트래픽**까지 숨길 수는 없다. 방어자는 파일 겉모습이 아니라 내부 심볼과 네트워크 행위를 기준으로 헌팅해야 한다.
